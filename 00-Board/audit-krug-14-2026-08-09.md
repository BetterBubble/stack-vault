# Аудит стека круг 14 — находки ревизора-ломателя 2026-08-09

Круг НЕ пустой: в `autonomous-feature.js` — файле, который тринадцать кругов читали только по верхам, —
нашлось одно крупное и четыре средних. SSH-классификатор `guard.sh` (Приоритет 2) прогнан запуском по
всем путям и держится — там пусто.

Всё только чтение, кроме этого файла. Логику `autonomous-feature.js` гонял тем же сухим харнессом, что и
`test-autonomous-feature.js` (настоящий поток управления, субагенты — заглушки); SSH-классификатор — живым
запуском `guard.sh` с подменой `AGENT_ROLE` и `agent_id`, роль стека серверу запрещена целиком, поэтому
пробы под `implementer`/`director`. Все скрипты воспроизведения — в скратчпаде.

## 1. КРУПНОЕ — отчёт на доску режется на середине `tasks`, и первыми теряются порядок мержа и «прод неизвестен»

**КЛАСС:** расхождение обещанного и сделанного · молчаливая потеря самого важного.

**ЧТО.** Данные в утренний отчёт уходят так (строки 1088-1135):

```js
const reportData = Object.assign({}, result, { tasks: (result.tasks||[]).map(t => { const {history,...rest}=t; return rest }) })
...
`Данные: ${JSON.stringify(reportData).slice(0, 9000)}.`
```

Порядок ключей в `result` (строки 1070-1078): `status, nightShift, tasks, mergeOrder, deployAuthorized,
needsHumanFirst, failures, scopeReport, ...`. `tasks` идёт ТРЕТЬИМ и объёмен: в каждом элементе — `delivery`
с полем `prBody` (описание PR: «что сделано · зачем · что тестировалось · числа» — по природе 1-2 КБ). Срез
`slice(0, 9000)` на нормальной ночной очереди из 3-5 задач режет строку **посередине массива `tasks`**, а всё,
что сериализовано ПОСЛЕ него, — `mergeOrder`, `needsHumanFirst`, `failures`, `note` про порядок мержа — в
отчёт не попадает вовсе. Комментарий на строках 1132-1134 утверждает, что удаление `history` эту проблему
закрыло («первым при переполнении терялось то, что стоит в конце объекта… Отчёту нужны не попытки, а их
итог») — но `history` убран, а `prBody` остался, и одного его хватает на переполнение.

**ВОСПРОИЗВЕДЕНИЕ.** `scratchpad/repro-real.js` — ночная очередь из 5 независимых задач, у каждой обычное
PR-описание (~1.5 КБ):

```
задач: 5 · mergeOrder в result: 5
длина полного JSON result-проекции: 11712
длина куска в отчёт (cap 9000): 9000
JSON в отчёте валиден? false — Unterminated string in JSON at position 9000
mergeOrder доехал в отчёт? false
needsHumanFirst доехал? false
failures доехали? false
note (мержить по порядку) доехал? false
```

Отдельно `scratchpad/repro-c2.js`: одна задача, деплой оборвался сбоем инструмента (статус
`deploy-tool-failed-state-unknown`). В `result.needsHumanFirst` лежит тревога «СОСТОЯНИЕ ПРОДА НЕИЗВЕСТНО,
проверь руками». При `prBody` в 12 КБ эта строка до данных отчёта не доезжает: `в данных отчёта есть
"needsHumanFirst"? false`, `есть "НЕИЗВЕСТНО"? false`.

**ПОСЛЕДСТВИЕ.** Ровно то, ради чего ночь и существует, теряется первым. Читатель отчёта — только что
проснувшийся Президент — получает обрезанный, невалидный JSON, в котором нет ни порядка мержа (а стек
мержится строго снизу вверх, иначе диффы врут), ни строки «сначала руками», ни списка именованных отказов.
Пишущий отчёт агент либо молча опустит эти разделы, либо додумает их из битого текста. Худший случай —
`deploy-tool-failed-state-unknown`: единственная строка, которая обязана быть громкой («тронули прод или нет
— неизвестно»), исчезает тише всех. Это не про попытки, которые «не жалко»: обрезается итог.

**ЧТО ЧИНИТЬ.** Резать не весь объект, а только объёмное. Варианты по убыванию надёжности: (1) собрать
компактную проекцию для отчёта, где у `tasks` остаются только имя/статус/ветка/база/числа, а `prBody`/`prUrl`
не входят вовсе (они и так в `mergeOrder`/`delivery`, нужных отдельно); (2) сериализовать поля по отдельности с
индивидуальными лимитами, чтобы `mergeOrder`, `needsHumanFirst`, `failures` были неусекаемыми; (3) как минимум
поставить критичные поля (`needsHumanFirst`, `mergeOrder`, `failures`) ПЕРЕД `tasks` в объекте и урезать
`prBody` каждой задачи до N символов. Слепой `slice` по всему JSON терять обязан наименее важное, а сейчас
теряет наиболее важное.

## 2. СРЕДНЕЕ — статус `ready-stop-pressed` выпал из `mergeOrder`, а мёртвый `ready-window-closed` в нём остался

**КЛАСС:** недостижимый статус в фильтре · потерянная инструкция по мержу (тот самый класс, о котором файл
предупреждает дважды — строки 957-961 и 993-994).

**ЧТО.** Фильтр порядка мержа (строки 962-966):

```js
.filter(x => x.branch && (x.status === 'ready' || x.status === 'ready-window-closed' ||
                          x.status === 'deployed' || ... ))
```

`ready-window-closed` не выставляется НИГДЕ (grep по файлу даёт только эту строку фильтра — окно вырезано
2026-08-05, статус остался мёртвым). А `ready-stop-pressed`, который РЕАЛЬНО выставляется на строке 735
(стоп нажат к моменту деплоя), в фильтр не попал. Задача при этом полностью готова: гейт пройден, ветка
закоммичена и запушена (`Доставка` идёт ДО фазы деплоя), деплой лишь ждёт человека.

**ВОСПРОИЗВЕДЕНИЕ.** `scratchpad/repro-krug14.js`, блок A (стоп нажат между подготовкой и деплоем):

```
статус задачи: ready-stop-pressed · ветка: auto/d · pushed: true
mergeOrder: []
=> ветка потеряна из mergeOrder? true
```

**ПОСЛЕДСТВИЕ.** Готовая, запушенная ветка исчезает из раздела «порядок мержа» утреннего отчёта: её базы,
факта пуша и ссылки на PR там нет. Задача видна только в §6 «отказы по именам», где про этот статус прямо
написано «Отказом работы это не является» — то есть человек читает «работа готова», но инструкции, как её
влить, не получает. В стеке зависимостей это рвёт колонну: если следующая ветка отведена от этой, её база
указывает на ветку, которой в порядке мержа нет.

**ЧТО ЧИНИТЬ.** В фильтре `mergeOrder` заменить мёртвый `ready-window-closed` на живой `ready-stop-pressed`
(либо добавить второй, а мёртвый убрать). Заодно — это ровно то, о чём предупреждает комментарий на 957-961:
перечень статусов явный, каждый новый обязан быть дописан и сюда; проверка «все выставляемые статусы
присутствуют в mergeOrder-фильтре ИЛИ в blocked/skipped» просилась бы в тест.

## 3. СРЕДНЕЕ — сбой разведки называется «нажат AGENTS_OFF» и советует `rm` несуществующего файла

**КЛАСС:** неверно названный отказ (кардинальный грех этого файла — «отказы обязаны различаться по имени») ·
инструкция человеку, ведущая не туда.

**ЧТО.** Разведка перед прогоном обёрнута fail-closed (строки 408-411):

```js
} catch (e) {
  log(`Разведка не удалась (${e && e.message}) — считаю стопы активными (fail-closed)...`)
  prep = { agentsOff: true, autonomyOff: true, note: String(e && e.message) }
}
```

Дальше `if (prep && prep.agentsOff)` (строка 413) даёт `status: 'blocked-agents-off'` и
`note: 'Снять может только человек: rm ~/.claude/AGENTS_OFF'`. Само решение НЕ стартовать — верное. Неверны
имя и совет: файла `AGENTS_OFF` не существует, упал субагент разведки (сеть, спавн).

**ВОСПРОИЗВЕДЕНИЕ.** `scratchpad/repro-e.js` (разведка бросает исключение):

```
status: blocked-agents-off
note: Снять может только человек: rm ~/.claude/AGENTS_OFF
prep.agentsOff: true (файла AGENTS_OFF на самом деле нет — это был сбой разведки)
log разведки: Разведка не удалась (subagent не поднялся: сеть недоступна) — считаю стопы активными...
```

`log` честен, но в `result` (и в отчёт) уходит именно статус `blocked-agents-off` и совет `rm`. Человек
выполнит `rm ~/.claude/AGENTS_OFF` → «файл не найден» → тратит время не там, при том что настоящая причина
(разведка не поднялась) осталась только в логе. Сравни, как аккуратно получили собственные имена
`blocked-empty-queue` и `blocked-not-autonomizable`: пустая очередь и неавтономизируемый план разведены, а
сбой разведки слит с ручным стопом.

**ЧТО ЧИНИТЬ.** В `catch` разведки ставить отдельный статус (напр. `blocked-preflight-failed`) с note «разведка
не поднялась (<текст>), стопы считаю активными из осторожности; проверь, что субагенты вообще запускаются» —
без совета `rm`. Fail-closed по решению оставить как есть; разъехаться должны имя и первый шаг человека.

## 4. СРЕДНЕЕ — гейт «доказан» без механического вывода: `mechanical` не обязателен схемой и не проверяется кодом

**КЛАСС:** заявленный, а не доказанный гейт — то есть ровно тот self-cert, против которого построен весь файл.

**ЧТО.** Центральная идея (строки 125-127): «гейт обязан быть ДОКАЗАН, а не заявлен. Раньше здесь было только
суждение агента — то есть Opus проверял Opus». Но схема `GATE` (строки 120-130) требует лишь `['passed']`;
`mechanical` (дословный вывод `gate-check.sh`) — необязательное поле. Код принимает вердикт по
`gatePassed = !!(gate && gate.passed)` (строка 626) и `mechanical` не читает нигде. Контролёр, который
пропустит механический прогон и вернёт `{passed:true}`, проходит молча — именно то, что объявлено
недопустимым.

**ВОСПРОИЗВЕДЕНИЕ.** `scratchpad/repro-krug14.js`, блок D (заглушка гейта возвращает `{passed:true}` без
`mechanical`):

```
статус: ready
жалоба на отсутствие mechanical в логах? false
```

**ПОСЛЕДСТВИЕ.** Гарантия «гейт подтверждён детерминированной проверкой» держится только на послушании
субагента-контролёра, хотя весь смысл механического вывода — не полагаться на слово того, кто проверяет.
Ниже (строки 546-604) контролёр подробно инструктируется приложить вывод дословно, но ничто не enforce'ит,
что он это сделал; регресс в персоне controller или пропуск шага не будет замечен.

**ЧТО ЧИНИТЬ.** Внести `mechanical` в `required` схемы `GATE` И проверять его непустоту при
`gatePassed=true`: пустой/отсутствующий `mechanical` при `passed:true` → трактовать как непройденный гейт
(«вердикт без доказательства не вердикт»). Это симметрично тому, как артефакт отката проверяется командами, а
не по самоотчёту (строки 867-886).

## 5. СРЕДНЕЕ — `dependsOn` с несколькими НЕзависимыми предками честен только к последнему

**КЛАСС:** частично выполненное обещание · молчаливо выпавший скоуп предка.

**ЧТО.** База ветки берётся как вершина ТОЛЬКО последней зависимости (строки 437-462), а объединение скоупа
(`scopeUnion`) собирается обходом цепочки `dependsOn` от этого одного родителя вверх. Если задача `c` зависит
от `['a','b']`, где `a` и `b` независимы друг от друга, то `parent = b`, `ancestry = [b]`, и код/скоуп `a` в
базу и в `scopeUnion` не входят вовсе. Проверка провала предка (`failedDep`, строка 443) корректно смотрит на
ВСЕ deps, а вот база и скоуп — только на последний.

**ВОСПРОИЗВЕДЕНИЕ.** `scratchpad/repro-krug14.js`, блок B (`c` зависит от независимых `a` и `b`):

```
база c (из промпта impl): auto/b
промпт impl:c упоминает ветку/задачу «a»? false
scopeUnion для c: ["services/b/**","tests/b/**","services/c/**","tests/c/**"]   ← «a» отсутствует
```

**ПОСЛЕДСТВИЕ.** Задача, объявленная зависящей от `a` и `b`, строится только на `b`: изменений `a` в её базе
нет. Если `c` действительно нужен код `a` — она либо сломается, либо повторит его и даст конфликт при мерже
(ловится человеком/гейтом ниже, не молча в прод). Плюс `scopeUnion` без скоупа `a` может дать ложное
«вне скоупа» на честной работе, опирающейся на `a`. Форма редкая (обычно очереди линейны `a→b→c`, там всё
верно), потому средним, а не крупным: последствие ограничено и ловится downstream.

**ЧТО ЧИНИТЬ.** Либо честно задокументировать и провалидировать на старте, что поддерживаются только линейные
цепочки (несколько независимых предков → `badDeps`), либо собирать `scopeUnion` и предупреждать по ВСЕМ deps,
а не только по последнему (база в git всё равно одна — тогда прямо сказать в отчёте, что код остальных
предков в базе отсутствует и их надо влить раньше).

## Что проверил и нашёл исправным

**SSH-классификатор `guard.sh` (Приоритет 2) — пусто, держится.** Прогнал живым гейтом по всем путям
(`scratchpad/probe.sh`, `probe2.sh`), роль `implementer`+`agent_id` (путь воркера, где вердикт
чтение/запись реально решает allow/deny):

- 15 пишущих форм — все DENY: `tee -a`, `ss -K`, `docker logs; docker restart` (второй сегмент),
  `find -fprintf`, `journalctl --rotate`, `date -s`, `sysctl -w`, `systemctl --machine … restart`,
  `cat … > файл`, `awk system()`, `sed w/файл`, `printf >&/файл`, `env X=1 restart`, `nice … restart`,
  `tail | sh`.
- 8 читающих форм — все ALLOW: `journalctl -o json`, `docker --context prod ps`, `git -C … log`,
  `sed -n /error/p`, `awk {print $NF}`, `grep -E "a|b"` (пайп в кавычках), `ps aux`, `systemctl status`.
- `ssh_db_query`: `SELECT count` ALLOW; `SELECT setval`, `DELETE`, `SELECT pg_read_file`, writable-CTE
  (`WITH … UPDATE … RETURNING`) — DENY; mongo `find` ALLOW, `findAndModify` DENY.
- `ssh_tail`: обычный tail ALLOW; `grep` с `; systemctl restart` и `file` с backtick — DENY.
- `ssh_download`: в `/tmp` ALLOW; в `~/.claude/hooks` и `~/claude-stack` — DENY.
- Контроль домов: роль `stack` на любой ssh-инструмент и на прямой `ssh` в Bash — DENY целиком; роль
  `director` без нажатого стопа на прод-меняющий ssh — ALLOW (окно вырезано 2026-08-05, прод держат кнопки
  стопа + норма CLAUDE.md + запрет воркеру, не классификатор). Это соответствует замыслу, не дефект.

**`autonomous-feature.js` — прочитан построчно (1146 строк).** Исправным подтвердил: обёртки try вокруг всех
`agent()` (падение любого субагента не уносит прогон и итог); различение «сбой инструмента» и «провал гейта»
в фикс-цикле; fail-closed повторной проверки стопа перед деплоем; путь к деплою только через подтверждённую
точку отката; артефакт отката проверяется командами, а не самоотчётом, и дописывается задним числом без
отката исправного деплоя; `needsFirst` собирается по признаку `morningTop`, а не по перечню; именованные
отказы очереди (`blocked-empty-queue`, `blocked-not-autonomizable`, `badDeps`); стартовый гейт плана (скоуп,
числа приёмки, строка апрува, «Что НЕ трогаем» в двух формах); нормализация аргументов-строки; пропуск
зависимых при провале основания. `node test-autonomous-feature.js` — 149 ok, 0 провалов (но тест написан
автором и слеп там же — все пять находок выше тест НЕ ловит).
