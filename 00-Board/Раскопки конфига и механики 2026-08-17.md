Область: `~/.claude` — механика, которая реально исполняется. Цель — отличить правило, которое держит механика, от правила, которое держится дисциплиной агента.

Метод: чтение, grep по структуре и **пробы на живом гейте** (`GUARD_TEST_RUN=1`, синтетические payload'ы, живые файлы не тронуты). Каждый вывод про механику подтверждён вердиктом `guard.sh`, а не чтением комментария: комментарии в `guard.sh` местами расходятся с кодом (см. пп. 2 и 3 раздела «Объявлено, но не работает»). Serena для этой области бесполезна — bash и markdown, LSP-символов нет.

## Развилки

1. **«Read-only» воркеры пишут и удаляют код — закрывать?** Пробы: explorer/verifier/controller через Bash пишут и делают `rm` в `~/tacticum`, ALLOW при любой роли сессии. Варианты: (а) оставить на тексте персоны; (б) правило «субагент типа explorer/verifier/controller не пишет в `AGENT_CODE_ROOT`» — но тип воркера в payload'е гейта ОТСУТСТВУЕТ, нужен новый признак; (в) убрать Bash из `tools:`. **Рекомендую (б)** с честной оговоркой, что признака сейчас нет: у verifier'а Bash — это его работа, забирать нельзя.
2. **Периметр правится Edit/Write кем угодно, включая субагента.** Пробы: Write `settings.json`, Write `agent-stack.conf`, Edit `guard.sh` — ALLOW. Одна правка `AGENT_CODE_ROOT` снимает A2 и PUSH и переживает рестарт. Варианты: (а) оставить (замысел «дифф виден»); (б) закрыть Edit/Write субагентам, оставить ролям; (в) закрыть всем кроме роли `stack`. **Рекомендую (б)**: для стоп-кнопок эта же дыра найдена и закрыта 09.08 (`guard.sh:2284-2294`), для часовых — нет.
3. **Что делать воркеру ПРИ ОТКАЗЕ ГЕЙТА — не сказано нигде.** Инструкция есть в трёх текстах отказа из полутора десятков; в персонах воркеров про отказ гейта ни строки. Варианты: (а) абзац в 5 персон; (б) в `agent-company.md`; (в) в сам текст отказа. **Рекомендую (а)+(в)**: отказ обязан называть следующий шаг там, где читается, иначе воркер повторяет команду — в журнале это уже видно (аудит 05.08: одна команда шесть раз).
4. **`tacticum_prod` — единственный сервер БЕЗ `MODE`.** В `~/.ssh-manager/.env`: `zu_demo` restricted, `adp_emb`/`project_hub`/`gateway` readonly, `helm`/`teststand` unrestricted, у `tacticum_prod` ключа нет вовсе; `src/policy.js:161` — нет режима значит unrestricted. **Рекомендую** поставить readonly и открывать через `grant-write.sh`: это прод каталога профилей, сейчас самый открытый из семи.
5. **Права воркера в team-режиме не равны его дефиниции.** Подробности и проверка — в разделе «Уточнение по team-режиму» ниже. **Рекомендую** сначала выяснить, читается ли frontmatter `tools:` в team-режиме вообще.
6. **`gate-check.sh` и `stack-doctor.sh` не вызываются автоматически ниоткуда.** 363 теста и весь гейт мержа существуют, пока кто-то вспомнит. Варианты: (а) доктор в SessionStart (дорого — сотни запусков `guard.sh`); (б) по расписанию с троттлингом как `memory-maintenance`; (в) оставить ручным. **Рекомендую (б)** для доктора; `gate-check` оставить ручным — он про конкретный worktree.
7. **Права на серверы решает роль СЕССИИ, а не спавнер.** `guard.sh:1620-1623` — сознательно: воркеры наследуют `AGENT_ROLE` окна, поэтому explorer под director идёт на серверы, под stack — нет. **Рекомендую оставить**: обоснование в коде названо честно, альтернатива отобрала бы ssh у рабочих воркеров.
8. **Ротации журналов нет:** `permission-denied.test.log` 18 МБ, `permission-denied.log` 1,8 МБ, растут только вверх. **Рекомендую** усечение по размеру в `memory-maintenance.sh` — там уже есть троттлинг и место для такой работы.

## Уточнение по team-режиму (проверка гипотезы «воркеры идут без своих MCP»)

Вопрос: относится ли п. 5 только к team-режиму или к обычному Task-спавну тоже. Проверено по 1,2 ГБ транскриптов `~/.claude/projects` (1028 файлов субагентов с `.meta.json`).

**Task-спавн: MCP-инструменты у воркеров ЕСТЬ и используются.** Агрегат вызовов внутри sidechain: `mcp__ssh-manager__ssh_execute` 2205, `mcp__serena__replace_content` 481, `mcp__basic-memory__write_note` 254, `mcp__serena__activate_project` 253, `mcp__serena__replace_symbol_body` 235, `find_symbol` 150, `get_symbols_overview` 65, `find_referencing_symbols` 65, плюс живые вызовы `mcp__taiga__*` и `mcp__wiki-mcp__*`. **Значит гипотеза «воркеры идут без своих MCP» для Task-спавна этими данными НЕ подтверждается.**

**Типы воркеров разрешаются правильно.** `.meta.json` каждого субагента несёт `agentType`. По всей истории: implementer 148, general-purpose 105, explorer 90, controller 75, critic 64, verifier 30. В выборочной сессии `b9493deb`: 7 запросов `subagent_type:"explorer"` → ровно 7 файлов с `agentType:"explorer"`. Подмены кастомной персоны встроенным агентом нет.

**Чего в персонах нет, а в рантайме появляется.** В транскриптах есть запись `"attachment":{"type":"deferred_tools_delta","addedNames":[…]}` — харнесс доклеивает субагенту инструменты сверх `tools:` (в одном образце 103 имени: WebFetch, WebSearch, SendMessage, Task*, Monitor, Cron*, `mcp__basic-memory__canvas` и прочее). То есть `tools:` — стартовый набор, а не жёсткий белый список. Этим объясняются 1323 вызова WebFetch и вызовы `mcp__helm-analyst__*`, `mcp__iva-mcp__*`, `ssh_upload` в sidechain, которых нет ни в одной из пяти дефиниций.

**Наблюдение без вывода.** За всю историю sidechain: `Grep` — 2 вызова, `Glob` — 0, при 37 353 вызовах `Bash`. Grep и Glob объявлены во всех пяти `tools:`. Это может быть и поведением (воркеры грепают через Bash), и отсутствием инструмента. Различить по транскриптам нельзя: система-промпт в них не сохраняется.

**Чего проверить НЕ МОГУ.** Своим Task-спавном не проверю: у меня нет инструмента `Task` (есть только `TaskCreate`/`TaskList` — трекер todo, другое). Утверждение про team-режим основано на моём собственном наборе инструментов, про Task-спавн — на истории вызовов. Прямого сравнения «одна и та же дефиниция, два способа запуска» не делал.
