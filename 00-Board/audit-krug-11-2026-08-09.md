## 1. Страховка компактации — фантом: PreCompact не доставляет контекст, а post-compact после сжатия утверждает модели, что состояние спасено

**КЛАСС:** код построен на механизме, которого нет (тот же класс, который сам `post-compact.sh`
описывает и обходит — для СЕБЯ, но не для соседнего файла).

**ЧТО.** `pre-compact.sh:29-31` отдаёт `hookSpecificOutput.additionalContext` для события
`PreCompact` — просьбу переписать `session-state` до сжатия. Но `PreCompact` НЕ входит в перечень
событий, для которых `additionalContext` доставляется модели. Перечень (SessionStart, Setup,
SubagentStart, UserPromptSubmit, UserPromptExpansion, PreToolUse, PostToolUse, PostToolUseFailure,
PostToolBatch, Stop, SubagentStop) записан в этом же стеке ДВАЖДЫ — `post-compact.sh:14-19` и
`cli-compat.md:68` — и подтверждён живой докой (code.claude.com/docs/en/hooks, fetch 09.08.2026):
у PreCompact из decision-контроля только `decision: "block"`, доставки контекста нет. То есть вся
страховка «спасти состояние перед сжатием» уходит в debug-лог и до модели не доезжает НИКОГДА.

Вторая половина хуже: `post-compact.sh:84` после сжатия сообщает модели «актуальное состояние — в
`01-Sessions/session-state.md` (её переписал хук PreCompact перед сжатием)». По пункту выше это
утверждение ложно всегда: PreCompact ничего не переписывал и переписать не просил. Модель сразу после
потери контекста направляется к чекпойнту с заверением о его свежести — а он свеж лишь настолько,
насколько роль писала состояние по ходу.

Третий край — контур стека: `AGENT_VAULT=~/stack-vault` (roles.zsh:243), а `~/stack-vault/01-Sessions`
не существует (состояние стека — `30-Sessions/stack-state.md`; команды `checkpoint.md:5` и
`wrap.md:20` это прямо оговаривают, хуки — нет). Плюс карта персон `post-compact.sh:73-74` не знает
роли `stack` → после сжатия stack-сессии печатается «Роль окна не определена (ни реестр, ни
AGENT_ROLE)» — ложь: роль определена, её просто нет в словаре.

**ВОСПРОИЗВЕДЕНИЕ.**

**ПОСЛЕДСТВИЕ.** Автосжатие — регулярное событие длинных сессий. В момент, ради которого страховку
строили, не происходит ничего из обещанного: состояние не спасается, а восстановительная подсказка

которой никто не обеспечил, — в контуре стека ещё и по несуществующему пути. Норма обещает механизм в

(несуществующий путь `04-Sessions`) — теперь в пустоту уходит не путь, а весь месседж.

**ЧТО ЧИНИТЬ.** Классом, не формой: (1) перенести доставку pre-compact-инструкции на документированный
канал — тот же мост, что уже построен в `post-compact.sh` (флаг + UserPromptSubmit), либо признать

против `30-Sessions/stack-state`), роль `stack` — в карту персон; (4) снять «PreCompact спасает
состояние» из четырёх мест нормы или заменить на настоящий механизм. Плюс строка в `cli-compat.md`
про PreCompact — реестр совместимости этого факта не знает, хотя оба соседних файла его цитируют.

## 2. Полный стоп: раннеры произвольного кода проходят на НЕВИННЫХ формах — `./deploy.sh` ALLOW при `bash deploy.sh` DENY

**КЛАСС:** граница принятого долга. Круг 10 разделил: самообфускация (`G=git; $G commit`) — принятый
долг, закрывается только песочницей; невинные формы, которые агент пишет сам собой, — дефект. Задание
круга — проверить, что на невинных формах похожего обхода нет. Он есть, и не про git.

**ЧТО.** Под `AGENTS_OFF` Bash режется по четырём условиям (`guard.sh:1065-1066`): WRITE_VERB, git,
INTERP, GIT_MUTATE. INTERP сознательно объявляет интерпретатор записью («что делает его код,
регулярка не знает» — `guard.sh:1038-1042`), и `bash deploy.sh`, `python3 x.py`, `node x.js` под
стопом получают DENY. Но ровно то же действие в соседнем написании проходит: прямой запуск скрипта
(`./deploy.sh`, `scripts/deploy.sh`) и раннеры, исполняющие произвольные рецепты
(`make deploy`, `npm run build`, `npx prettier --write .`, `yarn build`, `cargo build`,
`go build`), плюс запись без глагола (`tar -xf`, `unzip`, `sqlite3 … DELETE`). Все эти формы агент
пишет естественно посреди задачи — стоп нажимают асинхронно, и не заметивший его агент продолжает
именно такими командами.

**ВОСПРОИЗВЕДЕНИЕ** (песочный HOME с нажатым стопом, роль lead, настоящий `guard.sh`, cwd — песочный
git-репо; контроли подтверждают, что стоп активен):
```
git commit -m wip          => DENY   (контроль: стоп работает)
git log                    => ALLOW  (контроль: чтение живо)
bash deploy.sh             => DENY   (INTERP)
sh deploy.sh               => DENY
./deploy.sh                => ALLOW  ← тот же скрипт, другое написание
scripts/deploy.sh          => ALLOW
make deploy · make -C build all · make        => ALLOW
npm run build · npm ci · npm test · pnpm build => ALLOW
npx prettier --write .     => ALLOW  (перезапись исходников)
yarn build · cargo build · go build ./...     => ALLOW
tar -xf a.tar · unzip a.zip                   => ALLOW (запись файлов)
sqlite3 db.sqlite "DELETE FROM t"             => ALLOW (запись в БД)
pip install requests       => DENY   (случайно: «install» из WRITE_VERB)
```

**ПОСЛЕДСТВИЕ.** Инвариант «при AGENTS_OFF не меняется ничего» ложен для форм БЕЗ самообфускации —
тир кругов 6/8/9, не тир принятого долга. Асимметрия `bash x.sh` DENY / `./x.sh` ALLOW — то же
доказательство недосмотра, каким круг 8 доказывал недосмотр по git-подкомандам (асимметрия с
`config`). `npm run`/`make` — это исполнение shell-рецептов, то есть ровно тот интерпретатор, для
которого цена fail-closed под стопом уже принята.

**ЧТО ЧИНИТЬ.** Классом, в духе уже принятого INTERP: под стопом (и только под ним) считать записью
(а) прямой запуск пути в позиции команды (голова сегмента — `\S*/\S+` или `./…`), (б) известные
раннеры рецептов: make, npm, npx, yarn, pnpm, cargo, go, gradle/gradlew, mvn, bun, (в) двуликие
архиваторы/БД по нагрузке: `tar` с `x`, `unzip` без `-l`, `sqlite3` с не-SELECT — либо целиком, по
цене INTERP («читать есть чем»). Полное закрытие класса — всё равно песочница (`tech-debt.md:174-178`),
но эта граница отделяет невинное от самообфускации, и держать её дёшево. Git-часть границы цела —
см. «исправное».

## 3. Вооружение канала сигналов: пять живых сниппетов Monitor без обязательного поля `description` — вызов не проходит валидацию схемы

**КЛАСС:** сниппет в норме не проходит схему инструмента. Этот же класс уже ломал канал «во всех
восьми местах» с `timeout_ms` (`cli-compat.md:47`) — тогда починили только `timeout_ms`.

**ЧТО.** Схема `Monitor` этого харнесса: `"required": ["description", "timeout_ms", "persistent"]`.
Канонический сниппет (`signals.md:105-107`) и кикофф-сниппеты `director.md:43`, `lead.md:28` поле
несут. Не несут — и, значит, дают ошибку валидации вместо вооружения:
- `creator.md:37` и `planner.md:38` — единственный сниппет вооружения этих ролей;
- `lead.md:272` — перевооружение при смене адреса (`become <адрес>`), самый горячий случай:
  монитор старого адреса уже не тот, нового не встанет;
- `stop-reminder.sh:103` — подсказка агенту, у которого монитор УЖЕ умер (страховочный путь
  рекомендует нерабочий вызов ровно в момент, когда сработала страховка);
- `signal-status.sh:102` — та же подсказка «Поставь: Monitor({…})» без description.
Примеры в шапках `signal-watch.sh:5,28` и `stuck-check.sh:22` — тот же дефект в комментариях
(агент копирует и их).

**ВОСПРОИЗВЕДЕНИЕ.**
```
схема Monitor (ToolSearch, этот харнесс)  => "required": ["description", "timeout_ms", "persistent"]
grep -rn 'Monitor({' ~/claude-stack/roles/ ~/.claude/hooks/*.sh | grep -v description
  => creator.md:37 · planner.md:38 · lead.md:272 · stop-reminder.sh:103 · signal-status.sh:102
     · signal-watch.sh:5,28 · stuck-check.sh:22
```

**ПОСЛЕДСТВИЕ.** Роль, следующая персоне дословно, получает InputValidationError на первом шаге
онбординга; если не станет отлаживать чужой вызов — канал не вооружён, и наступает ровно то, о чём
предупреждает `signals.md`: «сигналы будут лежать… у простаивающей роли — никогда». Для creator и
planner это единственный путь вооружения; для lead — потеря канала при смене адреса без рестарта.

**ЧТО ЧИНИТЬ.** Добавить `description: "сигналы to:<роль>"` во все семь мест. И механизацию классом:
проверка доктора «сниппет `Monitor({` в персонах/хуках обязан нести все required-поля схемы» — класс
уже дважды дорогой (timeout_ms → description), третье обязательное поле появится тем же путём.

## Гипотезы (без полного воспроизведения — не находки)

- **Проверка доктора «пока пуста» даёт ложный BAD на ЦИТАТЕ фразы.** Воспроизведено в песочнице:
  персона, где «Пока пуста» стоит только внутри исторической сноски-цитаты, при непустой памяти
  получает `bad`. Живые тексты не триггерят — починка круга 10 сознательно пересказывает
  («стояло утверждение, что памяти ещё нет»), не цитируя. Латентно: следующий, кто процитирует
  историю дословно, покрасит доктора в красный. Чинить не предлагаю — комментарий проверки честно
  говорит «сторожит именно эту фразу»; достаточно знать при будущих правках персон.
- **`Workflow({…})` и `ScheduleWakeup` — инструменты, не подтверждённые ни одним фактом.**
  `director.md:277` запускает ночной прогон вызовом `Workflow({name: 'autonomous-feature', …})`;
  `director.md:192` и `verify-checklist.md:155` советуют `ScheduleWakeup`. В реестре инструментов
  этой сессии нет ни того, ни другого (ToolSearch: «No matching deferred tools»; для сравнения —
  `PushNotification` упоминается самим харнессом в доке Monitor, а планировщик здесь называется
  `CronCreate`). `cli-compat.md` — реестр «что проверено фактом» — про оба молчит. Проверить из
  чужой сессии нельзя (наборы инструментов сессионны), поэтому гипотеза; но если `Workflow` нет,
  ночной автоном не стартует вовсе — а чеклист и так честно держит «ночной автоном не обкатан ни
  разу». Дёшево закрыть: одна живая проба из сессии ГД + строка в `cli-compat.md`.
- **Персоны `verifier`/`critic` всё ещё утверждают о состоянии — в безопасную сторону.** «Она уже
  не пуста» (verifier.md:78, critic.md:103) — утверждение о состоянии рядом с собственной моралью
  «описывай механизм, а не состояние». Протухнет только если память опустошат; цена ошибки —
  «прочитай первым делом» об пустой каталог, не потеря. Отдельной правки не стоит; заметить при
  следующем касании файлов.

## Проверка починок круга 10 (главное задание) — держатся

1. **Персоны `verifier`/`critic`:** «пока пуста» снята, механизм описан (в контекст едет только
   `MEMORY.md`-оглавление, тела читаешь сам), противоречия с фактом нет: у verifier 9 заметок +
   `MEMORY.md`, у critic 2 + `MEMORY.md` — тексты говорят «уже не пуста, прочитай первым делом».
   Историческая сноска пересказывает, а не цитирует — проверку доктора не триггерит.
2. **Проверка доктора (`stack-doctor.sh:994-1014`) — все четыре стороны пробами** (дословная логика
   блока, песочный HOME): фраза + непустая память → BAD (ловит) · живые тексты → OK · фраза +
   отсутствующая/пустая память → OK («пока верно») · цитата фразы + непустая память → BAD (ложное,
   латентное — в гипотезы).
3. **Граница git-долга на невинных формах ЦЕЛА.** Под стопом DENY: `git -C repo commit` ·
   `git --git-dir=.git commit` · `git -c user.name=x commit` · `command git commit` ·
   `cd sub && git commit` · `for d in …; do git -C $d commit; done`. Глобальные флаги между `git` и
   подкомандой разобраны (`GIT_INVOKE`, `guard.sh:220-222`), обёртка `command` ловится по литералу.
