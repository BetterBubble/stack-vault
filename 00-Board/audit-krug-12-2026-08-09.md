# Аудит стека круг 12 — находки ревизора-ломателя 2026-08-09

Только чтение, кроме этого файла. Пробы гейта — в песочнице скратчпада (подменённый `HOME`,
одноразовый git-репо, песочная кнопка стопа и песочный реестр собраны через переменную — приём
кругов 10–11, `GUARD_TEST_RUN=1`). Живые кнопки, реестр, память, git-головы не тронуты; на серверы
не ходил. Области круга: главная — проверка починок круга 11 (`RUNNER` в guard.sh, оба
compact-хука, сниппеты `Monitor`, `verify-checklist`); новые — восемь непроверенных хуков построчно
(`statusline`, `board-sweep`, `deliverables-sweep`, `open-lead`, `roles-free`, `permission-denied`,
`tool-failure-log`, `signal-send`), команды `morning`/`catchup` на логику, сквозная проверка
утверждений `HANDBOOK.md` запуском.

## ГЛАВНОЕ: три починки круга 11 из четырёх держатся, но у четвёртой — RUNNER — лекарство от ложных отказов открыло дыру в обратную сторону: читающее СЛОВО в хвосте отпирает пишущую команду под полным стопом. Пять находок.

Направление, которого круг боялся (ложные отказы на чтении под стопом), закрыто добротно: все
семнадцать читающих форм проходят. Но исключение для чтения написано как «в хвосте есть читающее
слово», а не «нагрузка целиком читающая» — и ровно этим же файлом строк на сто ниже уже выучен
урок, что так нельзя (`ssh_query_readonly` судит SQL правильно). Вторая линия круга — норма и
карта: починка PreCompact остановилась на хуках и не тронула четыре места нормы, которые
по-прежнему обещают несуществующую страховку, а карта автоматики в HANDBOOK не знает четырёх
хуков из четырнадцати.

## 1. Полный стоп: исключение `RUNNER_READ` ищет читающее слово ГДЕ УГОДНО в хвосте — пишущая команда с читающим словом внутри проходит

**КЛАСС:** проверка «содержит читающий токен» вместо «состоит только из чтения» — зеркало урока,
уже записанного в этом же файле для git («белый список, якорь на позиции подкоманды, судим каждую
клаузу») и для SQL (`ssh_query_readonly`: одна инструкция, первый глагол из белого списка).

**ЧТО.** Починка круга 11 добавила к запрету раннеров таблицу читающих форм `RUNNER_READ`
(guard.sh, блок после `RUNNER`). Направление ложных отказов закрыто верно (см. «исправное»). Но
`runner_writes()` для каждого раннера берёт хвост до следующего раннера и пропускает его, если
`RUNNER_READ[head]` **нашёлся где-нибудь в хвосте**. Регэкспы таблицы не заякорены на позицию
подкоманды: `\bSELECT\b` у psql/sqlite3/mysql, `\bversion\b|\blogs\b|\binfo\b` у kubectl/docker,
`\benv\b` у go срабатывают на аргументах, именах объектов и вложенных подзапросах.

**ВОСПРОИЗВЕДЕНИЕ** (песочный HOME с нажатым стопом через переменную, роль lead, настоящий
`guard.sh`; контроли: `git commit` DENY, `git log` ALLOW):
```
psql -c "INSERT INTO audit_log SELECT * FROM tmp_rows"        => ALLOW  (INSERT!)
sqlite3 db.sqlite "DELETE FROM t WHERE id IN (SELECT id FROM u)" => ALLOW  (DELETE!)
sqlite3 db.sqlite "UPDATE t SET x=1 WHERE id IN (SELECT …)"   => ALLOW  (UPDATE!)
mysql -e "DROP TABLE users; SHOW TABLES"                      => ALLOW  (DROP!)
redis-cli SET counter 0 GET counter                           => ALLOW  (SET!)
go env -w GOFLAGS=-mod=mod                                    => ALLOW  (пишет env-файл)
kubectl delete pod version-checker                            => ALLOW  («version» в имени пода)
kubectl delete deployment logs-collector                      => ALLOW  («logs» в имени)
docker kill web-info                                          => ALLOW  («info» в имени)
контроли дыры: terraform apply => DENY · docker rm app => DENY · yarn remove left-pad => DENY
· docker ps && sqlite3 db "DROP TABLE t" => DENY (раннеры судятся по отдельности — это цело)
```

**ПОСЛЕДСТВИЕ.** `INSERT INTO … SELECT` и `DELETE … WHERE id IN (SELECT …)` — не экзотика, а
самый ходовой вид пишущего SQL; имена подов/контейнеров со словами `logs`/`version`/`info` — норма
любого кластера. То есть под `AGENTS_OFF` записи в БД и удаления в кластере проходят на формах,
которые агент пишет сам собой, — тот же тир, что находка 2 круга 11, только дыру внесла сама
починка. Асимметрия «`sqlite3 "DELETE FROM t"` DENY / `sqlite3 "DELETE … (SELECT …)"` ALLOW» —
доказательство недосмотра того же вида, каким круг 11 доказывал недосмотр по `./x.sh`.

**ЧТО ЧИНИТЬ.** Классом, и класс в файле уже есть: (1) для SQL-двуликих (`sqlite3`, `psql`,
`mysql`) звать существующий `ssh_query_readonly()` — он в этом же файле, судит правильно (одна
инструкция, первый глагол белого списка) и написан ровно для этого; (2) для остальных якорить
читающую форму на ПОЗИЦИЮ подкоманды (первое слово после головы и её флагов), а не искать по
хвосту; (3) `redis-cli` — все слова нагрузки из белого списка, а не «есть хоть одно»; (4) в тест
доктора — пары «пишущая команда с читающим словом внутри» из воспроизведения выше.

## 2. Починка PreCompact остановилась на хуках: норма в четырёх местах по-прежнему обещает «состояние спасает хук PreCompact», прямо противореча самому хуку

**КЛАСС:** правило в двух редакциях — хук говорит «страховки нет и не чинится», норма говорит
«страховка есть». Хвост находки 1 круга 11: из «ЧТО ЧИНИТЬ» выполнены пункты про хуки (1–3),
пункт 4 — снять обещание из нормы — не выполнен нигде.

**ЧТО.** `pre-compact.sh:4-9` теперь честно пишет: «ЭТОТ ХУК НЕ ДОСТАВЛЯЕТ НИЧЕГО МОДЕЛИ, И ЭТО
НЕ ЧИНИТСЯ ЗДЕСЬ … текст уходит в debug-лог и до модели не доезжает НИКОГДА». А норма — нет:
- `session-lifecycle.md:38` — «перед сжатием контекста состояние спасает хук `PreCompact`»;
- `session-lifecycle.md:40` — «Пассивная страховка: хук `pre-compact` — состояние успеет записаться»;
- `roles/director.md:130` — «Страховку перед сжатием держат хуки `PreCompact` (спасает состояние)»;
- `roles/lead.md:232` — «`PreCompact`, а `PostCompact` возвращает тебя к сохранённому состоянию»;
- `HANDBOOK.md:885` — «до сжатия контекста просит переписать заметку состояния».
Плюс недоделка в самом хуке: сообщение (мёртвая буква, но след в debug-логе) по-прежнему называет
`01-Sessions/session-state.md` для ВСЕХ контуров — в контуре стека (`AGENT_VAULT=~/stack-vault`)
такого каталога нет, состояние живёт в `30-Sessions/stack-state.md`. Пункт «развести контуры в
ОБОИХ хуках» выполнен только в `post-compact.sh` (там проверено пробами — держится, см. ниже).

**ВОСПРОИЗВЕДЕНИЕ.**
```
sed -n '4,9p' ~/.claude/hooks/pre-compact.sh      => «до модели не доезжает НИКОГДА»
grep -n 'PreCompact' session-lifecycle.md roles/director.md roles/lead.md HANDBOOK.md
                                                  => пять строк с обещанием спасения
echo '{"hook_event_name":"PreCompact",…}' | HOME=$SB AGENT_VAULT=$SB/stack-vault pre-compact.sh
                                                  => msg: «ПЕРЕПИШИ заметку 01-Sessions/…»
```

**ПОСЛЕДСТВИЕ.** Роль, читающая свою персону или session-lifecycle (а перечитать персону ей велит
сам post-compact), узнаёт о страховке, которой нет, — и планирует запись состояния «на этап», а не
«на каждый ход», хотя правило `ASSUME INTERRUPTION` в том же файле строкой выше говорит обратное.
Ложное обещание страховки опаснее её отсутствия — формулировка самого `pre-compact.sh:12-13`.

**ЧТО ЧИНИТЬ.** Снять/переписать пять строк нормы под факт («страховки перед сжатием нет; спасает
только запись по ходу; после сжатия PostCompact возвращает к последнему записанному состоянию»);
в `pre-compact.sh` — либо развести контуры в тексте сообщения, либо сократить сообщение до
честного следа «сжатие случилось» без инструкции, которую некому исполнить.

## 3. HANDBOOK §18 «Что происходит само»: карта автоматики не знает 4 регистраций из 14

**КЛАСС:** карта отстала от факта — в разделе, чья заявленная цель «то, что делается само, я не
замечаю, пока оно работает».

**ЧТО.** `HANDBOOK.md` §18 говорит «Десять регистраций в settings.json» и перечисляет их таблицей.
Фактически регистраций **14**; в карте отсутствуют: `stop-nudge.sh` (второй хук на `Stop`),
`tool-failure-log.sh` (`PostToolUseFailure` — журнал сбоев инструментов, заведён 06.08),
`diff-shorten.sh` и `pr-reminder.sh` (оба `PostToolUse`). Туда же мелкий дрейф соседней строки:
`HANDBOOK.md:695` обещает «532 проверки» доктора — живой прогон печатает «550 ok, 2 варн».

**ВОСПРОИЗВЕДЕНИЕ.**
```
python3: json.load(settings.json) → перечислить hooks   => 14 строк (список в ход-логе круга)
grep -n 'Десять регистраций' ~/claude-stack/HANDBOOK.md => §18
bash ~/.claude/hooks/stack-doctor.sh | tail -1          => «всё чисто: 550 ok, 2 варн»
```

**ПОСЛЕДСТВИЕ.** Ровно тот сценарий, от которого раздел заведён: перестанет работать невидимый
хук (журнал сбоев, напоминание о PR) — симптом будет выглядеть как что-то другое, а карта скажет,
что такого механизма и нет. Плюс «на вопрос "что у меня есть" — сверяйся с HANDBOOK, и только с
ней» (CLAUDE.md): единственный разрешённый справочник неполон.

**ЧТО ЧИНИТЬ.** Дописать четыре строки в таблицу §18, число «десять» заменить на живое (или убрать
число вовсе — оно дрейфует). Счётчик проверок доктора в §695 либо снять, либо округлить («~550»).
Механизация классом: проверка доктора «каждая регистрация из settings.json упомянута в §18
HANDBOOK» — дешёвый греп, класс уже второй раз дорогой (та же карта в круге 5 не знала событий).

## 4. `statusline.sh`: фоллбэк роли по `session_name` не знает `stack` — рецидив класса круга 11 в соседнем словаре

**КЛАСС:** «роль есть, а словарь не знает» — тот самый класс, который круг 11 нашёл в
`post-compact.sh` (PERSONA без `stack`). Починили один словарь, второй такой же в соседнем хуке
не проверили.

**ЧТО.** `statusline.sh:161`: при пустых реестре и `AGENT_ROLE` роль угадывается из
`session_name`, но принимается только из списка `("director", "lead", "creator", "planner",
"controller")` — `stack` в списке нет. `MARK` (иконки, :164-165) роли `stack` тоже не знает —
это безвредно (генерик `●`), а вот фоллбэк теряет роль целиком.

**ВОСПРОИЗВЕДЕНИЕ.**
```
sed -n '156,165p' ~/.claude/hooks/statusline.sh   => список без stack
```

**ПОСЛЕДСТВИЕ.** Малое: путь срабатывает только когда нет ни реестра, ни env (например, ручной
`claude --resume --name stack` мимо `roles.zsh`) — тогда окно стека остаётся без сегмента роли.
Но класс дефекта ровно тот, что вчера чинили, и дешевле закрыть его во всех словарях разом.

**ЧТО ЧИНИТЬ.** Добавить `stack` в кортеж :161 (и, по вкусу, иконку в `MARK`). Механизация: список
ролей в трёх местах (`PERSONA` post-compact, кортеж statusline, `MARK`) — кандидат на одну
проверку доктора «словари ролей согласованы между собой и с roles.zsh».

## 5. `verify-checklist.md:83` «Валит только ПУСТАЯ строка» — неточно: гейт валит и непустую строку апрува без Президент/ГД/лид

**КЛАСС:** норма описывает механизм чуть шире, чем он есть, — мелкое расхождение слова и кода в
только что переписанном разделе.

**ЧТО.** Чеклист: «Валит только ПУСТАЯ строка: тогда план не предъявлен в проверяемом виде». Код
(`gate-check.sh`, блок `--plan`): пункт зелёный при `bool(m) and ok_who`, где `ok_who` требует в
значении `Президент|ГД|director|лид|lead`. Непустая строка без этих слов — красный пункт.

**ВОСПРОИЗВЕДЕНИЕ** (песочный репо):
```
план с «апрув: лид, 2026-08-09 (план не размечал никто)»  => ✔ (третья форма проходит — верно)
план с «апрув: устно в чате, вчера вечером»               => ✗ «апрув самовыданный агентом»
```

**ПОСЛЕДСТВИЕ.** Малое: лид, написавший строку в вольной форме по чеклисту («любая непустая
пройдёт»), получит красный гейт и пойдёт искать поломку не там. В сторону безопасности, не дыры.

**ЧТО ЧИНИТЬ.** Одно слово в чеклисте: «Валит пустую строку И строку без Президент/ГД/лид» — либо
ослабить `ok_who` в гейте, если три канонические формы считать примером, а не перечнем. Первое
дешевле и честнее: формы три, так и проверяем.

## Гипотезы (без полного воспроизведения — не находки)

## Проверка починок круга 11 (главное задание)

1. **`RUNNER` под стопом — направление ложных отказов ЗАКРЫТО.** 17 читающих форм из задания —
   все ALLOW: `docker ps|logs|inspect` · `kubectl get|describe` · `helm list` · `psql -c 'SELECT 1'`
   · `mysql -e 'SELECT 1'` · `redis-cli GET` · `sqlite3 .tables|SELECT` · `go version|vet` ·
   `npm ls|view` · `make -n|--dry-run` · `tar -tf` · `unzip -l` · `docker logs | grep`. Пишущие
   формы круга 11 по-прежнему DENY: `./deploy.sh` · `make deploy` · `npm run build` · `rsync -an`
   (последний — ложный отказ на dry-run, `-an` не матчится читающим `(?:^|\s)-n`; мелочь, принял
   в цену fail-closed). Дыра в обратную сторону — находка 1.
2. **`pre-compact.sh`/`post-compact.sh`.** post-compact прогнан пробами по всем сценариям: stack →
   верный путь `30-Sessions/stack-state.md` и персона; lead/director → `01-Sessions` и персона;
   реестр сильнее env; без роли — честное «не определена»; доставка одноразова (второй промпт
   молчит); протухший флаг (>24ч) молчит; кривой JSON — тихий exit 0. `agent-stack.conf` окружение
   уважает (`${VAR:-}`) — затирания AGENT_VAULT нет. pre-compact честен в шапке, но см. находку 2
   (норма + контуры в теле сообщения).
3. **Сниппеты `Monitor` — все живые места несут `description`:** creator.md:37 · planner.md:38 ·
   lead.md:28,272 · director.md:43 · signals.md:105-107 · signal-watch.sh:5,28 · signal-status.sh:105
   · stop-reminder.sh:104 · stuck-check.sh:22-23. Поля схемы (`description`, `timeout_ms`,
   `persistent`) на месте везде, команды внутри валидны (скрипты существуют, `--new` у stuck-check
   есть). Держится.
4. **`verify-checklist.md` §69** приведён к норме 09.08: старт от разметки не зависит, три формы
   строки апрува, получасового ожидания нет, заголовок датирован верно; `gate-check --plan`
   подтверждает третью форму пробой. Держится — кроме одного неточного слова (находка 5).
