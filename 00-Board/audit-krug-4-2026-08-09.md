# Аудит стека круг 4 — находки ревизора-ломателя 2026-08-09

Только чтение, кроме этого файла; все пробы — в песочнице скратчпада (подменённый `HOME`,
одноразовые vault, реестры и репозитории; живые кнопки, реестр и память не тронуты).
Области круга: шесть починок круга 3 · `gate-check.sh` целиком · `mcp-doctor.sh` ·
персоны ролей против дефиниций воркеров. Девять доказанных находок, по убыванию последствия.
Сами починки круга 3 в основном держат: пять из шести прошли все пробы (см. «исправное»),
новых дыр от них — две мелкие (находки 5 и 6, обе в `check-links.sh`).

## 1. Гейт приёмки: ПУСТОЙ файл плана и ПУСТЫЕ метрики проходят строгий режим молча — проверка испаряется без следа

**КЛАСС:** проверка, которая не может провалиться (моя область №1) — «вход передан, но пуст»
неотличим от «всё проверено». Худший вариант для деплойного гейта.

**ЧТО.** В `gate-check.sh` три входа с одной болезнью:

- `--plan <файл>`: файл существует, но пуст → `ptxt` пустой → ветка `if ptxt:` пропускает ОБЕ
  проверки («строка апрува», «Что НЕ трогаем»), а ветка `else: unchecked_item("апрув плана")`
  не срабатывает, потому что PLAN передан (`gate-check.sh:268-315`). Ни в `checks`, ни в
  `unchecked` пункта нет — апрув плана исчезает из отчёта вовсе.
- `--metrics <файл>` с содержимым `{}`: цикл `for name, spec in m.items()` не делает ни одной
  итерации, `unchecked` не пополняется (`gate-check.sh:170-182`). Приёмка по числам «проверена»
  нулём проверок.
- (для сравнения: пустой `--scope` ведёт себя правильно — всё вне скоупа, провал.)

**ВОСПРОИЗВЕДЕНИЕ** (репозиторий-фикстура на ветке `feat/k4`, чистое дерево):
```
$ : > plan-empty.md; echo '{}' > m-empty.json
$ GATE_STRICT=1 GATE_ACK_UNCHECKED="скоуп,гейт приёмки" gate-check.sh <repo> \
    --metrics m-empty.json --plan plan-empty.md --json
ok_overall: True · blocking_unchecked: [] · в checks про метрики/план: []   rc=0
```
Строгий режим, вердикт зелёный, при этом ни апрув плана, ни одна метрика не проверялись —
и этого НЕ ВИДНО нигде: ни в проваленных, ни в «НЕ проверено», ни в «принятых ограничениях».

**ПОСЛЕДСТВИЕ.** Ночной пайплайн собирает значения флагов из переменных; пустая переменная уже
один раз давала здесь вечный цикл (комментарий в шапке скрипта), теперь пустой ФАЙЛ даёт
зелёный деплойный гейт. Это обход всей идеи «GATE_STRICT: непроверенное = провал»: непроверенное
перестаёт числиться непроверенным. Контролёр, прикладывающий вывод «дословно» (обе персоны это
требуют), приложит зелёное.

**ЧТО ЧИНИТЬ.** (1) `--plan`: пустой/нечитаемый текст → `add("план читается", False, …)` — по
образцу уже существующей ветки исключения. (2) `--metrics`: пустой объект после разбора →
`add("метрики разобраны", False, "файл есть, но метрик в нём ноль")`. Общее правило: «вход
передан» обязан приводить либо к проверкам, либо к провалу — но никогда к тишине. Плюс два
теста доктора на эти входы.

## 2. Под полным стопом `AGENTS_OFF` проходит запись `mcp__basic-memory__canvas` — файл создаётся в обход стопа

**КЛАСС:** дыра гейта (5) — обратная сторона находки 5 круга 3: там классификатор по имени
ложно запрещал чтение, здесь он пропускает ЗАПИСЬ.

**ЧТО.** `canvas` у basic-memory — «Create an Obsidian canvas file … will be saved as
title.canvas» (это его собственная схема): инструмент создаёт файл в vault. Слово «canvas» не
глагол — шаблон `MCP_WRITE_NAME` (`guard.sh:202-205`) его не матчит, в явном списке `MCP_WRITE`
(`guard.sh:185-195`) его нет, в `MCP_READ_EXCEPTIONS` тоже. Итог — под полным стопом разрешён.

**ВОСПРОИЗВЕДЕНИЕ** (песочница, кнопка в подменённом HOME; полный перебор инструментов живых
серверов — в «исправном»):
```
mcp__basic-memory__canvas        -> ALLOW   ← запись файла проходит стоп
mcp__basic-memory__write_note    -> DENY    (для сравнения: явный список работает)
mcp__serena__safe_delete_symbol  -> DENY    (первое слово «safe», но есть в MCP_WRITE — верно)
```

**ПОСЛЕДСТВИЕ.** Малое по площади (один инструмент, только в момент аварийного стопа), но
направление худшее из двух возможных: «запись прошла мимо стопа» — ровно то, что комментарий
классификатора называет недопустимым. Инвариант «при AGENTS_OFF не меняется ничего» ложен.

**ЧТО ЧИНИТЬ.** Добавить `mcp__basic-memory__canvas` в `MCP_WRITE` (рядом с `write_note`).
Заодно решить судьбу `create_memory_project` — он ловится глаголом, но явный список надёжнее
шаблона для известных имён.

## 3. `mcp-doctor.sh` печатает значения секретов из `args` stdio-сервера — вопреки собственному «НИКОГДА»

**КЛАСС:** расхождение обещания и поведения (моя область №2) + утечка секрета в транскрипт.

**ЧТО.** Шапка скрипта: «Значения токенов, Bearer и env-переменных не печатаются НИКОГДА».
Правило держится для `headers.Authorization` (только длина), значений `env` (только имена) и
чужого текста (`redact()`). Но `args` сервера печатаются сырыми в двух местах: строка таблицы
(`target` = command + args, `mcp-doctor.sh:482,513`) и строка фикса «увидеть настоящую ошибку:
cmd args» (`mcp-doctor.sh:329`). Токен в args — обычное дело у stdio-серверов (`--token …`,
`--api-key …`).

**ВОСПРОИЗВЕДЕНИЕ** (песочница, значение заведомо фальшивое):
```
$ … .mcp.json: {"k4-argtoken":{"command":"cat","args":["--token","sk-FAKEPROBE…"]}}
$ MCP_DOCTOR_ROOTS=$SB bash mcp-doctor.sh --only k4-argtoken | grep FAKEPROBE
  · k4-argtoken  stdio cat --token sk-FAKEPROBE00000000000000000000  не одобрен · …
```

**ПОСЛЕДСТВИЕ.** Вывод доктора попадает в транскрипт сессии (сам скрипт называет это причиной
правила) — то есть секрет уезжает в историю, откуда его не отозвать иначе как ротацией. Сегодня
в живых конфигах токенов в args нет (проверил `~/.claude.json` и найденные `.mcp.json` глазами) —
это мина, а не пожар.

**ЧТО ЧИНИТЬ.** Прогонять `target` и строку «увидеть настоящую ошибку» через `redact()` — он
уже ловит формы `token/key/secret + значение` и длинные строки. Одна строка в двух местах.

## 4. Баннер старта всегда завышает «протухло» — заголовок кэша pr-queue считается протухшей веткой

**КЛАСС:** починка 5 круга 3 несёт ошибку в самой строке баннера; ложная сводка каждый день.

**ЧТО.** `session-start.sh:76`: `PRQ="$(grep -c '^  !' "$PRC")"`. Кэш — полный вывод
`pr-queue.sh`, а тот печатает ШАПКУ таблицы `  !  дн  отстал  …` (`pr-queue.sh:97`), которая
сама начинается с `  !`. При протухших ветках добавляется и первая строка легенды
(`  ! — стоит ≥…`). Итог: PRQ = протухшие + 1 (шапка) [+1 легенда], ветка «все свежие»
(`session-start.sh:82`) недостижима никогда.

**ВОСПРОИЗВЕДЕНИЕ** (песочница: один репозиторий, одна СВЕЖАЯ недоставленная ветка, возраст 0 дн):
```
кэш: «  !  дн  отстал …» + «      0      1  repo1  feat/k4-probe»   ← протухших ноль
баннер: «веток ждёт мержа: 1, из них протухло 1 → …»                ← ложь
```

**ПОСЛЕДСТВИЕ.** Строка писалась против трения «ветка протухает незаметно» — а показывает
протухание там, где его нет. Сводке, которая всегда кричит, перестают верить — тот же механизм,
что с мусорной очередью решений (комментарий в `waiting-queue.sh`).

**ЧТО ЧИНИТЬ.** Считать по признаку строки данных, не по `!`: `PRQ=$(grep -cE '^  ! +[0-9]' …)`
(у шапки после `!` идут пробелы и «дн», у легенды — « — », цифры сразу — только у строк веток).
Тест: кэш с одной свежей веткой → «все свежие».

## 5. `--fix` в `check-links.sh` правит ссылки ВНУТРИ код-блоков и бэктиков — которые детекция осознанно исключает

**КЛАСС:** проверка починки 1 круга 3 (задание «работает ли --fix на однозначных») — сам fix на
прозе верен, но задевает то, что чекер объявляет неприкосновенным.

**ЧТО.** Детекция идёт по `strip_code(raw)` — «ссылки внутри кода — документация формата, а не
навигация» (`check-links.sh:77-81`). А правка идёт по СЫРОМУ тексту простым `str.replace`
(`check-links.sh:171-178`): если в файле есть хоть одна починяемая ссылка в прозе, заменятся ВСЕ
вхождения — включая код-блоки и бэктики.

**ВОСПРОИЗВЕДЕНИЕ** (песочница: файл с прозовой ссылкой + та же строка в ```-блоке и в бэктиках):
```
до:  Проза: `[[session-state-до]]` · ```…`[[session-state-до]]`…``` · `[[session-state-до]]`
$ check-links.sh --vault … --fix
после: ВСЕ ТРИ заменены на session-state-do
```

**ПОСЛЕДСТВИЕ.** Отчёты аудита этого стека нарочно кладут примеры битых форм в бэктики (круг 3
на это уже напоролся и починился бэктиками). Прогон `--fix` по vault перепишет такие примеры —
документация того, ЧТО было сломано, молча станет документацией того, чего сломано не было.

**ЧТО ЧИНИТЬ.** Делать замену по тем же правилам, что детекцию: например, применять replace к
`raw` посегментно, пропуская сегменты кода (регэксп из `strip_code` отдаёт границы), либо
заменять по позициям совпадений, найденным в очищенном тексте.

## 6. Регистронезависимая ступень чекера сверяет `san`, а не саму ссылку — ссылка с `:`/`/` и иным регистром молча объявляется кликающейся

**КЛАСС:** та самая «потеря класса „не кликается“», на которую задание велело смотреть; побочка
починки 1 круга 3, узкая.

**ЧТО.** Ступень «регистр перед транслитом» (`check-links.sh:131-133`) проверяет
`san.lower() in ci`, где `san` — ссылка после замены `:`/`/`→`-`. Для чистой разницы регистра
(`[[Дело]]` при `дело.md`) это верно — Obsidian резолвит без учёта регистра. Но если ссылка
содержит `:` или `/` И отличается регистром, Obsidian её НЕ откроет (в ссылке двоеточие, в имени
файла дефис), а чекер молчит: раньше такой случай при точном регистре попадал в «не кликается».

**ВОСПРОИЗВЕДЕНИЕ** (песочница: файл `про- дело.md`, ссылка `[[ПРО: ДЕЛО]]`):
```
$ check-links.sh --vault …
Итого: битых 0/0 · не кликается 0/0        ← ссылка не показана нигде; клик создаст заглушку
(контроль: `[[Дело]]`/дело.md — верно молчит; `[[миръ]]` при мир.md+mir.md — верно в битых,
 --fix её не трогает; `[[session-state-до…]]` — верно «не кликается» и чинится)
```

**ПОСЛЕДСТВИЕ.** Один узкий подкласс снова невидим — класс, ради видимости которого чекер и
устроен. На живых vault таких ссылок сейчас нет (прогон обоих чист), цена мала.

**ЧТО ЧИНИТЬ.** Сравнивать без учёта регистра САМУ ссылку (`link.lower()`/`anchorless.lower()`),
а совпадение `san.lower()` (с заменёнными `:`/`/`) относить к классу «не кликается» с целью из
индекса — не к «кликается».

## 7. Две редакции контролёра противоречат друг другу в норме апрува — рабочая копия несёт отменённую норму 05.08

**КЛАСС:** расхождение персоны и дефиниции (моя область №3); остаток прежней нормы — тот же
класс, что находка 2 круга 2 про CLAUDE.md, только внутри пары файлов одной роли.

**ЧТО.** Charter `~/claude-stack/roles/controller.md:46` (правка 04:55): допустимы ТРИ формы
строки апрува — `Президент…` · `ГД…` · `лид… (план не размечал никто)`, третья гейт НЕ валит
(решение 09.08: разметка плана не условие старта); гейт валит только пустую строку. Рабочая
копия `~/.claude/agents/controller.md:38` (той же ночи): «обязательна строка апрува
(`апрув: Президент…` / `апрув: ГД…`) — решение Президента 2026-08-05 ВЕРНУЛО апрув плана…
её отсутствие — провал гейта». Третьей формы нет, основание — отменённое решение.
Механика (`gate-check.sh:280`) при этом принимает и `лид` — код совпадает с charter.

**ВОСПРОИЗВЕДЕНИЕ.** Цитаты дословные, файлы и строки указаны; расхождение видно диффом двух
пунктов 3. Рабочая копия по собственной шапке существует «чтобы гейт срабатывал, даже если
charter не открыт» — то есть применяется ИМЕННО тогда, когда сверить не с чем.

**ПОСЛЕДСТВИЕ.** Контролёр, работающий по копии (штатный режим субагента — charter может быть
недоступен), провалит гейт крупной задачи с `апрув: лид…`, который по норме проходит: возврат
шлагбаума, убранного решением 09.08, в одном из двух текстов одной роли. Какая норма исполнится —
решает то, какой файл агент прочитал, дословно как в находке 2 круга 2.

**ЧТО ЧИНИТЬ.** Перенести в `agents/controller.md:38` формулировку трёх форм из charter (и
убрать ссылку на решение 05.08 как основание). Плюс — это уже третий случай «двух редакций
одной нормы» за сутки: доктору стоит сверять пары charter/копия хотя бы грепом по маркерным
строкам (формы апрува, вердикты).

## 8. `mcp-doctor.sh` при таймауте живого локального сервера ставит диагноз «порт закрыт — сервер не запущен»

**КЛАСС:** доктор врёт про причину — против его же смысла существования («называет причину, а
не „проверьте настройки“»); моя область №2, ветка «сервер отвечает медленно».

**ЧТО.** Всё, что curl завершил без HTTP-кода, падает в ветку `000` (`mcp-doctor.sh:413-428`),
а для localhost она печатает безусловное «локальный порт закрыт — сервер на этой машине просто
не запущен». Таймаут (порт открыт, сервер слушает, но не отвечает — повис, перегружен, ждёт
другой протокол) даёт тот же код 000.

**ВОСПРОИЗВЕДЕНИЕ** (песочница: сокет слушает 127.0.0.1:47631, принимает соединение и молчит 30 с):
```
── k4-slow · project · …/.mcp.json
  Причина: локальный порт закрыт — сервер на этой машине просто не запущен.   ← ложь
  curl:    curl: (28) Operation timed out after 3011 milliseconds…            ← правда рядом
```

**ПОСЛЕДСТВИЕ.** Человек по «Причине» пойдёт поднимать сервер, который поднят; настоящая
подсказка есть только в строке curl, которую «Причина» прямо опровергает. Цена — минуты разбора,
не потеря данных.

**ЧТО ЧИНИТЬ.** Различать по stderr curl: `(28)`/`timed out` → «порт открыт, но сервер не
ответил за N с — повис или отвечает не по протоколу»; `(7)`/`refused` → нынешний текст.

## 9. Под `AGENTS_OFF` ложно блокируется чтение `mcp__serena__open_dashboard`

**КЛАСС:** ложный отказ (мелкий) — тот же класс и той же механики, что находка 5 круга 3
(`build_context`), пропущенный при её починке: список исключений пополнили одним именем, а
шаблон глаголов по остальным живым инструментам не перебрали.

**ЧТО и ВОСПРОИЗВЕДЕНИЕ.** `open_dashboard` («Opens the Serena web dashboard in the default web
browser» — чтение, ничего не меняет) матчится глаголом `open` в `MCP_WRITE_NAME`. Проба под
стопом: `mcp__serena__open_dashboard -> DENY`; остальные 30+ читающих имён обоих серверов — ALLOW
(полный перебор в «исправном»).

**ПОСЛЕДСТВИЕ.** Микроскопическое (дашборд в момент аварийного стопа), но направление то же
неправильное: стоп на изменения отбирает чтение.

**ЧТО ЧИНИТЬ.** Добавить в `MCP_READ_EXCEPTIONS`. После этого перебор живых имён чист полностью.

## Гипотезы (без полного воспроизведения)

- **`fix_token_lines` печатает URL сырым** (`mcp-doctor.sh:373`): в ветке 401 для user/local-скоупа
  строка фикса подставляет `$url` без `url_safe()` — токен в query (`?api_key=…`) или `user:pass@`
  уйдёт в вывод. Не воспроизведено: нужен сервер в НАСТОЯЩЕМ `~/.claude.json`, менять его нельзя.
  Чинится тем же `url_safe`, что уже применён в таблице и в ветке 000.
- **Гонка снятия протухшего лока** (`session-end.sh:35-37`, `role-register.sh:100-105`): два
  ожидающих видят протухший лок, оба делают `rmdir` — второй `rmdir` может снять уже СВЕЖИЙ лок
  первого (каталог пуст), и оба войдут в секцию. Требует протухшего лока И двух претендентов в
  окне миллисекунд; не воспроизводил. Стандартное лечение — перед `rmdir` перечитать mtime под
  случайной задержкой, либо лок-файл с pid владельца.
- **Битый путь в `--plan` даёт rc=1 (НАРУШЕНИЕ)**, тогда как контракт в самом файле
