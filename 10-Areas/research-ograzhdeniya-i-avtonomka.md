# Ресерч: ограждения и автономка у других (вторая половина большого захода)

Первая половина — оркестрация и память — в отдельной заметке. Здесь: ограждения,
автономные прогоны, специфика Claude Code, приёмы «эффект сразу». Скоуп заказан 26.07,
поставлен в [[tech-debt]] («Большой ресерч: чужие стеки оркестрации агентов»).

**Все ссылки на доки — дата обращения 2026-08-05.** Где дата публикации у источника есть,
она названа отдельно. Где утверждение не подтверждено первоисточником — так и написано.

---

## Ответ на главный вопрос: структурное решение догоняющего гейта СУЩЕСТВУЕТ и лежит в его же CLI

Проблема сформулирована в [[tech-debt]]: «правило, которое смотрит на текст команды, всегда знает
только те формы, которые кто-то успел придумать» — девять кругов слома, 673 формы, 392 проверки,
четыре раза дыру вносила собственная починка.

**Чужой ответ на это один и тот же у всех, кто решал: не разбирать текст вообще, а поставить
границу там, где текст уже не важен — в ядре ОС (что процесс может писать и куда соединяться) либо
в модели-судье (что команда делает по смыслу).** Ни одно из найденных решений не является перечнем
форм. Два из них — родные для Claude Code 2.1.220, то есть доступны без установки чего-либо.

Проверено локально на его машине (2026-08-05): `~/.claude/settings.json` **не содержит ключа
`sandbox` вообще**, `permissions.defaultMode` не задан (значит Manual), allow 166 / ask 2 / deny 45,
хуков 11 событий. То есть оба структурных механизма выключены, а держит периметр текстовый разбор:
и `guard.sh`, и сам `permissions.deny`, где правила ровно того же догоняющего вида —
`Bash(*rm -rf*)`, `Bash(*rm -Rf*)`, `Bash(*rm -fR*)`, `Bash(*rm -fr*)`, `Bash(*rm -r -f*)`,
`Bash(*rm -f -r*)`, `Bash(*rm --recursive --force*)`. Семь правил на один `rm` — это тот же счётчик
форм, только в JSON.

## A. Ограждения

### A1. Встроенная песочница Bash: Seatbelt / bubblewrap, запрет на уровне syscall

**Что у них.** В Claude Code есть штатная песочница для инструмента Bash: `sandbox.enabled: true`
в `settings.json` плюс панель `/sandbox`. Изоляция двухслойная и обе половины — на примитивах ОС:
файловая система через **Seatbelt на macOS** и **bubblewrap на Linux/WSL2**, сеть — через локальный
прокси с списком разрешённых доменов. По умолчанию запись разрешена только в рабочий каталог и
временный каталог сессии; чтение — по всей машине, кроме заданных `denyRead`. Ключи:
`sandbox.filesystem.allowWrite / denyWrite / allowRead / denyRead / disabled`,
`sandbox.network.allowedDomains / deniedDomains / strictAllowlist / httpProxyPort`,
`sandbox.excludedCommands`, `sandbox.allowUnsandboxedCommands`, `sandbox.failIfUnavailable`,
`sandbox.credentials.files/envVars` с режимами `deny`/`mask`.
Источник: [Configure the sandboxed Bash tool](https://code.claude.com/docs/en/sandboxing).

Три детали, которые бьют прямо в его девять кругов:

1. **«Ограничения применяются ко всем дочерним процессам»** — то есть форма записи команды
   перестаёт что-либо значить. `find -de⏎lete`, `X=1 python`, `>|`, `sed -n 's/a/b/w/tmp/leak'`,
   `git -c core.pager='curl -T …'`, `\` + CRLF — все тринадцать форм восьмого круга и все четыре
   класса девятого пишут через один и тот же `write()`, и ядро его не пропускает. Разбирать нечего.
2. **Песочница сама запрещает запись в файлы, через которые команда могла бы расширить свою же
   политику:** `settings.json` всех скоупов, каталог managed-настроек, `.mcp.json` в корне проекта
   и в каждом каталоге из `--add-dir`, и — с v2.1.210 — цель симлинка, подставленного на место
   защищённого файла. Плюс запись вне рабочего каталога запрещена по умолчанию, а значит
   `~/.claude/hooks/guard.sh` из сессии в `~/tacticum` недостижим **структурно**. Это закрывает
   «самую дешёвую из семи прямых дыр» — `chmod -x guard.sh` — без единого нового правила.
3. **Режим auto-allow: песочные команды исполняются БЕЗ запроса разрешения.** Явные `deny`-правила
   и content-scoped `ask` (например `Bash(git push *)`) продолжают действовать, `rm` по `/` и
   домашнему каталогу всё равно спрашивает (маршрутизация через классификатор — с v2.1.218).

**Чем лучше его схемы.** Односторонность его гейта («не даёт пропусков, но даёт лишние отказы»)
здесь не нужна вовсе: граница не в тексте. Каждая из трёх названных им границ подхода
(posix-лексер снимает кавычки; перевод строки внутри кавычек; проверка подстановки не знает кавычек)
исчезает вместе с разбором. И главное — **это минус трение, а не плюс:** сейчас у него 166
allow-правил ровно для того, чтобы не спрашивать на каждую команду; auto-allow снимает вопрос
целиком для всего, что укладывается в границу.

**Чем хуже.** Три вещи, и их надо назвать честно:

- **Песочница накрывает только Bash.** MCP-серверы и хуки — отдельные процессы и исполняются на
  хосте без ограничений. У него весь тяжёлый периметр — `ssh-manager` (`ssh_execute`, `ssh_tail`,
  `ssh_download`), то есть **классификатор ssh на 392 проверки песочницей не заменяется вообще**.
  Это прямо сказано в [Choose a sandbox environment](https://code.claude.com/docs/en/sandbox-environments).
- Сетевой прокси решает по имени хоста из запроса клиента и по умолчанию TLS не терминирует —
  док сам называет domain fronting как способ уйти за список. Экспериментальный
  `network.tlsTerminate` (v2.1.199+) терминирует, но фильтрации содержимого не добавляет.
- Совместимость: `docker` несовместим (в `excludedCommands`), `watchman`/`jest` требует
  `--no-watchman`, Go-CLI (`gh`, `gcloud`, `terraform`) могут падать на проверке TLS под Seatbelt,
  `open`/`osascript` требуют `allowAppleEvents` (а он снимает изоляцию исполнения кода). Опасение
  26.07 «есть риск, что будет проблема в автономности агентов» **подтверждается частично и адресно**:
  проблемы есть, они перечислены и у каждой есть штатный обход. Отдельно про субагентов: они
  исполняются в том же процессе и наследуют конфигурацию песочницы — то есть воркеры не отвалятся.

**Брать или нет.** Брать, но узко и не как замену гейта: включить песочницу с auto-allow для
локального Bash и **оставить ssh-классификатор жить** — он закрывает то, что песочница не видит.
Это первое, что стоит сделать из всего ресерча.

### A2. Auto mode: классификатор вместо перечня — и опубликованные цифры, почему

**Что у них.** Режим `auto` (`permissions.defaultMode: "auto"`, только user/managed-скоуп) заменяет
запрос разрешения на **отдельную модель-судью**, которая смотрит на действие и блокирует то, что
выходит за рамки просьбы. Источник:
[Choose a permission mode](https://code.claude.com/docs/en/permission-modes).
Инженерный разбор с числами: [Claude Code auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode),
**дата публикации 2026-03-25**.

Устройство по этому разбору: четыре слоя — (1) встроенный список безопасных read-only инструментов,
(2) правки внутри проекта проходят без проверки, потому что видны в git, (3) двухступенчатый
классификатор: быстрый однотокенный фильтр со смещением в блокировку, затем цепочка размышления
только для помеченного, (4) серверная проба на prompt injection, просматривающая результаты
инструментов до того, как их прочитает агент.

Опубликованные измерения:

| Набор | Результат |
|---|---|
| 10 000 реальных вызовов | 1-я ступень: 8,5 % ложных отказов; весь конвейер — 0,4 % |
| 52 реальных «переусердствовал» | 1-я ступень ловит 93,4 %; весь конвейер 83 %, то есть 17 % пропусков |
| 1000 синтетических утечек данных | 2-я ступень: 5,7 % пропусков на обфусцированных попытках |

Ключевое проектное решение, которое стоит забрать даже без самого режима: **классификатор не видит
ни ответов модели, ни результатов инструментов — только сообщения пользователя и сами команды.**
Причина названа прямо: иначе агент «уговорит классификатор» рассуждениями, и через результаты
инструментов пойдёт инъекция. Цена — классификатор не знает происхождения значений (отсюда и правило
про `rm -rf "$VAR"`, где переменная не встречалась в разговоре: блокируется, потому что проверить
цель нельзя).

Что блокируется по умолчанию — список читается как оглавление его же гейта, только сформулированное
по смыслу, а не по подстроке: `curl | bash`, отправка чувствительных данных наружу, **прод-деплои и
миграции**, массовое удаление в облачных хранилищах, выдача IAM/repo-прав, изменение общей
инфраструктуры, необратимое уничтожение файлов, существовавших до сессии, force push,
`git reset --hard` / `git clean -fd` / `git stash drop`, `terraform destroy` и аналоги,
запись в секрет-менеджер, изменение DNS/TLS, мерж PR без человеческого одобрения, одобрение
собственного PR, отключение CI-проверок, переключение прод-фича-флага, туннель или reverse shell
наружу, печать живого токена в транскрипт или файл, **запуск автономного агентского цикла без
человеческого одобрения или песочницы** (`--dangerously-skip-permissions`, `--no-sandbox`),
запуск команды с флагом, снимающим защиту (`--insecure`), **запись в свои же транскрипты сессии в
`~/.claude/projects/*.jsonl`** (v2.1.205+, как защита в глубину — подделанная запись доедет до
каждой последующей проверки при возобновлении).

И механизм, которого у него нет вообще: **границы, названные в разговоре, работают как блокировка.**
Сказал «не пушь» или «дождись моего ревью перед деплоем» — классификатор блокирует совпадающие
действия, даже если правила по умолчанию их разрешают, и граница держится, пока он её не снимет
в следующем сообщении. Своё собственное суждение агента, что условие выполнено, границу не снимает.
Оговорка в доке: границы не хранятся как правила, классификатор перечитывает их из транскрипта,
поэтому компактизация может их потерять — для твёрдой гарантии нужен `deny`.

Падение при блокировке устроено как «отказал и продолжай»: агенту возвращается причина, он ищет
другой путь; при 3 отказах подряд или 20 за сессию auto mode выключается и возвращаются запросы.
В `-p` режиме повторные блокировки прерывают прогон, потому что спрашивать некого.

**Доступность у него подтверждена:** нужны Opus 4.6+ / Sonnet 4.6+ / Fable 5 на Anthropic API —
он на `claude-opus-5[1m]`; план — любой; версия — от 2.1.207 без переменных окружения, у него 2.1.220.

**Чем лучше его схемы.** Смотрит на смысл, а не на форму. Ни `\`+перенос внутри флага, ни
`#;`-комментарий, ни `>&файл`, ни версионный комментарий MySQL с `INTO OUTFILE` не «прячут»
действие от судьи, который читает команду как человек. Плюс он даёт то, чего текстовый гейт не
даёт в принципе: правило «не пушь до моего ревью», сказанное словами, начинает действовать.

**Чем хуже.** Тоже честно, и это важнее плюсов:

- **17 % пропусков на реальных «переусердствовал».** Это не барьер. Anthropic сама пишет: замена
  `--dangerously-skip-permissions` — большое улучшение; замена вдумчивого одобрения каждого
  действия — обмен ошибок классификатора на снижение усталости от запросов.
- **Вероятностный, а не детерминированный.** Его `stack-doctor.sh` обязан быть детерминированным
  (это его же требование из [[tech-debt]]) — классификатор в такую роль не годится и в доктор его
  вносить нельзя.
- **Стоит токенов и задержки** на каждую shell-команду и сетевую операцию.
- **При входе в auto mode отбрасываются широкие allow-правила** — «wildcarded interpreters» и
  правила `Agent`. У него под это попадают `Bash(python3*)`, `Bash(python *)`, `Bash(node *)`,
  `Bash(npx *)`, `Bash(yarn *)`, `Bash(pnpm *)`, `Bash(uv *)` — семь правил из 166. Правила не
  ломаются, а начинают проходить через классификатор: больше задержки, не отказы. Узкие
  (`Bash(npm test)`, `Bash(bash ~/.claude/hooks/*.sh*)`) переносятся как есть.

**Брать или нет.** Брать как **второй слой над песочницей**, а не вместо неё и не вместо гейта.
Осмысленная схема: песочница держит форму (что можно писать и куда соединяться), классификатор
держит смысл (стоит ли это делать), `guard.sh` держит его личные правила, которых нет ни у кого
(мерж в main руками, деплой по ОК, значения секретов никогда в git). Три слоя ловят разные классы,
и ни один не заменяет другой.

### A3. `@anthropic-ai/sandbox-runtime`: та же изоляция, но на весь процесс — включая MCP и хуки

**Что у них.** Отдельный пакет, оборачивающий произвольный процесс в те же примитивы
(`sandbox-exec` на macOS, `bubblewrap` на Linux, WFP на Windows — alpha) плюс прокси-фильтрация
сети. Запуск: `npm install -g @anthropic-ai/sandbox-runtime`, затем `srt "команда"` либо
`npx @anthropic-ai/sandbox-runtime claude`. Конфиг `~/.srt-settings.json`:
`network.allowedDomains / deniedDomains / allowUnixSockets / allowLocalBinding`,
`filesystem.allowWrite / denyWrite / allowRead / denyRead`, `mandatoryDenySearchDepth`,
`ignoreViolations`, `enableWeakerNestedSandbox`, `enableWeakerNetworkIsolation`, `allowAppleEvents`.
Источники: [README](https://github.com/anthropic-experimental/sandbox-runtime) и раздел
[Sandbox runtime](https://code.claude.com/docs/en/sandbox-environments#sandbox-runtime).
Статус — **beta research preview, формат конфигурации может меняться**; дату первого релиза
первоисточником не подтвердил.

Главная ценность для него — **`srt` накрывает MCP-серверы и хуки, которых встроенная песочница
не видит**. И безусловные запреты записи, независимые от конфига: `.bashrc`/`.zshrc`/`.profile`,
`.gitconfig`/`.gitmodules`, `.vscode/`, `.idea/`, **`.claude/commands/`, `.claude/agents/`**,
`.git/hooks`, `.git/config`. То есть класс «агент правит то, чем его же проверяют» закрыт местом,
а не перечнем — ровно тот приём, которым он сам закрыл композиционный класс на девятом круге
(«всё, что смотрит на текст, смотрит на результат одной функции»).

Две ловушки названы в доке прямо, и обе стоит запомнить:

- Без валидного `~/.srt-settings.json` рантайм **всё равно стартует**, режет сеть и сужает запись до
  внутренних путей. «Чистый старт не есть доказательство, что твои настройки загрузились».
  С `--settings` — наоборот, отказывается стартовать, если файл не читается.
- На Linux/WSL2 список запретов строится один раз при запуске: корень проекта покрыт надёжно,
  вложенные копии — поверхностным сканом, а созданное в сессии (`git init`, `git clone`) не покрыто
  вовсе. На macOS проверка идёт в момент записи, поэтому покрывает и вложенное, и созданное позже.
  **У него macOS — то есть попадает в сильную половину.**

**Чем лучше его схемы.** Единственное из найденного, что накрывает `ssh-manager` как процесс.
**Чем хуже.** Beta research preview с меняющимся конфигом под всей его работой; писать надо явно
разрешить `~/.claude`, `~/.claude.json`, `/tmp` и проект, иначе не заведётся; ограничивает
локальную сторону MCP-сервера, а **не удалённый сервер** — команда, ушедшая по разрешённому
соединению, ядру локальной машины уже не видна.

**Брать или нет.** Сейчас — нет; держать в поле зрения. Причина не в качестве, а в статусе: beta с
меняющимся форматом под контуром, где он работает каждый день, — это ровно то, что ломает работу
ночью. Пересмотреть, когда уйдёт слово preview.

### A4. Codex CLI: независимое подтверждение, что перечня форм не делает никто

**Что у них.** У Codex CLI то же разделение на два независимых регулятора:
`sandbox_mode` — `read-only` / `workspace-write` (по умолчанию) / `danger-full-access`, и
`approval_policy` — `untrusted` / `on-request` / `never`. Исполнение — Seatbelt на macOS,
Landlock + seccomp на Linux, отдельная реализация на Windows (`elevated`/`unelevated`).
В `workspace-write` сети по умолчанию нет, включается явно; `.git` и `.codex` защищены от записи
даже в записываемом режиме. Организация может запретить `never` через `requirements.toml`.
Источник: [Codex config file](https://learn.chatgpt.com/docs/config-file/config-basic).
**Списка допустимых текстов команд в конфигурации нет.**

**Чем лучше его схемы.** Ничем принципиально новым по сравнению с A1 — и это самая ценная часть
находки. Две независимые команды, решая одну задачу, пришли к одной архитектуре: **граница ОС ×
политика одобрения, ортогонально**. У него сейчас эти две оси слиты в один текстовый разбор,
который пытается быть и границей, и политикой.

**Брать или нет.** Брать идею разделения осей, не инструмент. Практический вывод: перестать
пытаться выразить «что можно» и «когда спрашивать» одним механизмом. «Что можно» → песочница,
«когда спрашивать» → `ask`-правила и классификатор, «его личные нормы» → `guard.sh`.

### A5. Для ssh-половины структурное решение есть, но оно на сервере, а не в агенте

**Что есть.** Ни одна изоляция на его машине не защищает удалённый хост: соединение разрешено, а
дальше команду исполняет чужой sshd. Структурный аналог белого списка тут один и он старый —
**forced command в `authorized_keys`**: `restrict,command="…"` перед ключом заставляет sshd
исполнять только заданную команду, что бы ни попросил клиент, и заодно снимает PTY и все
проброски; `PermitOpen` ограничивает пробросы портов конкретным хостом и портом. Источник:
[authorized_keys(5)](https://manpages.debian.org/experimental/openssh-server/authorized_keys.5.en.html).

**Чем лучше его схемы.** Различие в природе: авторизация происходит на стороне, которую агент не
контролирует и переписать не может, и не зависит ни от одной формы записи команды. Отдельный ключ
для агента с `restrict,command="/usr/local/bin/agent-ro"`, где скрипт-обёртка сам решает, что
позволено, — это перенос решения из «разбора текста у клиента» в «авторизацию у ресурса». Плюс
отдельный непривилегированный пользователь и `sudoers` под него.

**Чем хуже.** Трение сдвигается, а не исчезает: каждую новую нужную команду надо вносить на сервер,
и делать это надо на живом сервере, то есть под изменение, требующее его ОК. И это чужая
инфраструктура — там, где серверы заказчика, менять `authorized_keys` может быть попросту нельзя.

**Брать или нет.** Не сейчас, но записать как единственный честный ответ на «что даёт настоящий
барьер для ssh». Он не отменяет отказ Президента от барьера прода: барьер прода — про деплой,
а это — про периметр чтения. Если однажды захочется убрать 392 проверки, замена им — здесь,
а не в новом круге слома.

### Итог по A: чем это НЕ является

Ни один из пяти приёмов не закрывает всё. Разложение по слоям, чтобы не было иллюзии:

| Что нужно защитить | Что закрывает структурно | Что остаётся текстовым разбором |
|---|---|---|
| Локальная ФС и сеть из Bash | Песочница A1 (ядро) | — |
| `~/.claude/hooks/*`, `settings.json`, `.mcp.json` | A1 (вне cwd + явный список защищённых) и A3 | — |
| Свои транскрипты сессии | Auto mode A2 (v2.1.205+) | — |
| MCP-серверы и хуки как процессы | Только A3 (beta) | — |
| **Удалённый сервер через `ssh_execute`** | **Только A5, на сервере** | **весь классификатор, 392 проверки** |
| Смысл действия (деплой, force push, утечка) | A2, вероятностно, 17 % пропусков | его нормы в `guard.sh` |

## B. Автономные ночные и фоновые прогоны

### B1. Штатный headless: `-p` плюс флаги, и что у него уже есть под рукой

**Что у них.** `claude -p "…"` — неинтерактивный прогон; код выхода 0/не-0, ошибки внутри прогона
печатаются как результат в stdout. Флаги под автономку: `--permission-mode` (в том числе `dontAsk`
для «только предодобренное» и `auto`), `--allowedTools` / `--disallowedTools`, `--max-turns`,
`--output-format json|stream-json` + `--json-schema` (валидируется, невалидная схема — отказ на
старте, с v2.1.205), `--continue` / `--resume <id>` / `--fork-session`, `--session-id`, `--name`,
`--settings`, `--setting-sources`, `--append-system-prompt(-file)`, `--add-dir`, `--bare`.
Источники: [Run Claude Code programmatically](https://code.claude.com/docs/en/headless),
[CLI reference](https://code.claude.com/docs/en/cli-reference).

Три вещи, которые прямо относятся к его схеме:

- **`--bare`** отключает автозагрузку хуков, скиллов, плагинов, MCP, auto memory и CLAUDE.md.
  Док называет его рекомендованным для скриптов и обещает сделать поведением по умолчанию для `-p`.
  Для его ночных прогонов это **ловушка, а не подарок**: в `--bare` не сработает ни `guard.sh`,
  ни журнал воркеров, ни память. Знать про него надо именно чтобы не включить случайно.
- **Фоновые задачи при выходе:** background-shell убивается примерно через 5 секунд после результата;
  фоновые субагенты и воркфлоу ожидаются, но с v2.1.182 не дольше 10 минут
  (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`, `0` — без предела). Зависший воркер больше не держит
  прогон вечно — но и может быть срезан, если честно работает 11 минут.
- **SIGTERM** прерывает ход, убивает дерево процессов Bash-команды, **исполняет хуки `SessionEnd`**
  и выходит с кодом 143. То есть его `session-end.sh` при снятии ночного прогона отработает.

`--worktree` / `-w` создаёт изолированные worktree для параллельных ветвей (принимает `#<номер>`
или URL PR, сам фетчит и ветвится), `--bg` запускает сессию фоновым агентом и сразу возвращает
session ID, `--cloud` создаёт веб-сессию.

**Чем лучше его схемы.** У него ночная рутина записана в [[tech-debt]] как незакрытая: «слэш-команду
нельзя выполнить без сессии», сделана догоняющая половина — напоминание при первом старте.
**Док прямо снимает это ограничение:** пользовательские скиллы и кастомные команды работают в `-p`,
надо включить `/skill-name` в строку промпта, и Claude Code развернёт её перед прогоном. То есть
`claude -p "/tidy"` из cron — штатный путь, а не обход. Это самая дешёвая находка всего ресерча:
пункт долга закрывается одной строкой в crontab, при условии, что режим разрешений задан явно.

**Чем хуже.** Ничем — это тот же CLI. Оговорка одна: в `-p` при повторных блокировках классификатора
прогон прерывается, потому что спрашивать некого, значит для ночи нужен либо `dontAsk` с заранее
выписанными allow, либо песочница с auto-allow.

**Брать или нет.** Брать: `claude -p "/tidy"` по расписанию, режим `dontAsk`, `--max-turns`,
`--output-format json` в файл-отчёт, без `--bare`.

### B2. Что делают с откатом: чужого волшебства нет, и это стоит знать

**Что у них.** Штатные чекпойнты (`/rewind`) снимают состояние файлов перед каждым промптом, 100
последних на сессию, живут 30 дней (`cleanupPeriodDays`). Источник:
[Checkpointing](https://code.claude.com/docs/en/checkpointing).

**Пределы названы доком прямо, и они убивают идею «откат за меня»:**

- **изменения, сделанные bash-командами, не отслеживаются вовсе** — `rm`, `mv`, `cp` не откатить;
- **правки субагентов не восстанавливаются** — они ложатся вне чекпойнтов сессии, «используйте git»;
- симлинки и хардлинки при восстановлении пропускаются с предупреждением;
- внешние изменения и правки параллельных сессий не захватываются.

**Чем это лучше/хуже его схемы.** Хуже во всём, что важно для его ночей: у него работа идёт
воркерами в worktree, то есть **ровно тот случай, который чекпойнты не восстанавливают**. Его
собственная схема — ветка + PR + мерж руками — строго надёжнее, потому что откат в ней это git,
а не сессионное undo.

**Про падение на середине необратимой операции: чужого ответа нет.** Ни в одном первоисточнике за
этот заход не нашлось механизма, который откатывает половину применённой миграции или половину
деплоя. Всё, что предлагается, — не доводить до этой ситуации: PR вместо прямого пуша,
изолированный worktree на задачу, артефакт отката, подготовленный до применения. Его требование
«обязательный артефакт отката» из скилла `autonomous-feature` — то же решение, и оно не слабее
чужих. **Отдельно: это не «не подтверждено», а «искал и не нашёл» — если у кого-то это есть,
находка не публичная.**

**Брать или нет.** Не брать чекпойнты как механизм отката для воркеров — они там не работают.
Знать про `/rewind` как локальное undo для своих правок в диалоге, и не более.

### B3. Облачные routines и `--bg`: где ночь работает без человека

**Что у них.** Фоновые агенты (`--bg`, экран `/agents` — [background agents](https://code.claude.com/docs/en/agent-view))
и облачные routines по расписанию / по вызову API / по событию GitHub. Дату открытия research
preview для routines (14.04.2026) даёт вторичный источник, **первоисточником не подтвердил**;
у него в системе routines доступны через скилл `schedule`, и это облачные агенты.

**Чем лучше/хуже его схемы.** Ограничение, записанное у него в [[tech-debt]] («облачные routines не
видят локальные файлы, MCP и серверы»), в этом заходе не опровергнуто: `--cloud`-сессия исполняется
в VM Anthropic, до его `~/stack-vault`, `ssh-manager` и серверов оттуда доступа нет. Значит
маршрут для ночи один: локальный `claude -p` из cron/launchd.

**Брать или нет.** Не брать routines для ночной рутины стека. Брать `--bg` для параллельных
локальных прогонов, когда не нужно держать окно.

## C. Специфика Claude Code: чего он не использует из уже существующего

Сверено с его конфигом 2026-08-05, версия CLI 2.1.220.

**Хуки.** Использует 11 событий: `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`,
`PostToolUse`, `PreCompact`, `PostCompact`, `Stop`, `PermissionDenied`, `SubagentStart`,
`SubagentStop`. В CLI событий около тридцати. Источник: [Hooks](https://code.claude.com/docs/en/hooks).
Из неиспользуемых прямо в его задачи попадают четыре:

| Событие | Что делает | Зачем ему |
|---|---|---|
| `ConfigChange` | срабатывает при изменении файла конфигурации в сессии, **может заблокировать изменение** | пункт «агент правит то, чем его проверяют» — с той стороны, где песочницы нет (правка через MCP, правка вне cwd при отключённой изоляции) |
| `PostToolUseFailure` | срабатывает после неуспешного вызова инструмента | ночные прогоны: сейчас падение инструмента нигде не журналируется отдельно от отказа гейта |
| `TeammateIdle` | срабатывает, когда участник команды агентов ушёл в простой, **может не дать уйти в простой** | у него компания ролей и ночные прогоны — это штатный способ не дать очереди встать |
| `PermissionRequest` | срабатывает, когда вызову нужно решение о разрешении; отдаёт `decision.behavior: allow\|deny` и `updatedPermissions` | сейчас вся логика висит на `PreToolUse`; отдельное событие позволяет разделить «запрет» и «решение о разрешении» |

Ещё есть `Setup` (для `--init-only`/`--maintenance`), `PostToolBatch`, `StopFailure`,
`TaskCreated`/`TaskCompleted` (могут заблокировать создание/завершение задачи), `FileChanged`
(матчер — имена наблюдаемых файлов), `WorktreeCreate`/`WorktreeRemove`, `InstructionsLoaded`,
`UserPromptExpansion`, `MessageDisplay`, `Elicitation`/`ElicitationResult`, `CwdChanged`,
`DirectoryAdded`, `Notification`.

Отдельно: у `PreToolUse` есть значение `permissionDecision: "defer"` — «пропустить решение хука и
пойти обычным путём». Полезно там, где хук сейчас вынужден выбирать между `allow` и `deny`,
не имея оснований ни для того, ни для другого.

**Хуки не исполняются внутри песочницы Bash** — работают на хосте. И с v2.1.139 без управляющего
терминала, то есть `/dev/tty` им недоступен.

**Персоны субагентов.** В его пяти персонах (`controller`, `critic`, `explorer`, `implementer`,
`verifier`) заполнены только `name`, `description`, `tools`, `model`, `effort`. Не используется
восемь поддерживаемых полей — [Create custom subagents](https://code.claude.com/docs/en/sub-agents):

| Поле | Что даёт | Зачем ему |
|---|---|---|
| `isolation: worktree` | субагент работает в **временном** worktree, ветвясь по умолчанию от дефолтной ветки, а не от `HEAD` родителя; worktree сам убирается, если правок не было | закрывает пункт долга «36 worktree внутри `AGENT_CODE_ROOT`, размазаны по двум местам»: у `implementer` изоляция становится свойством персоны, а не дисциплины |
| `memory: user\|project\|local` | своя постоянная память субагента в `~/.claude/agent-memory/<имя>/` | воркеры сейчас не помнят ничего между вызовами; у `critic` и `verifier` накопленные грабли — это ровно то, что стоит переносить между заходами |
| `disallowedTools` | вычитает инструменты из унаследованного набора | сейчас `tools` перечисляется целиком — при добавлении MCP-сервера каждую персону надо править |
| `skills` | предзагружает **полное содержимое** скилла в контекст субагента | воркеру не надо угадывать, что вызвать |
| `mcpServers` | ограничивает набор MCP-серверов для этой персоны | `explorer` не должен вообще видеть `ssh-manager` пишущей половиной |
| `hooks` | хуки, ограниченные этой персоной | журнал воркера привязывается к персоне, а не к глобальному `SubagentStart` |
| `maxTurns` | предел ходов | ночь: воркер не уходит в бесконечный цикл |
| `permissionMode` | режим разрешений персоны (в auto mode игнорируется) | `explorer` мог бы быть `plan`, а не полагаться на перечень `tools` |

**Правила и свод.** `~/.claude/rules/` у него нет вовсе — вся always-loaded нагрузка в одном
`~/.claude/CLAUDE.md` (**21 865 байт, проверено**). Док: «целься меньше 200 строк на файл; более
длинные съедают контекст и снижают следование».

**Прочее, чего нет в конфиге:** `sandbox` (см. A1), `permissions.defaultMode`, `autoMemoryDirectory`,
`claudeMdExcludes`, `cleanupPeriodDays`. Плагины и маркетплейсы не используются — но чужие сборники
хуков ([karanb192/claude-code-hooks](https://github.com/karanb192/claude-code-hooks),
[CodyLunders/claude-code-hooks-library](https://github.com/CodyLunders/claude-code-hooks-library),
[ithiria894/awesome-claude-code-hooks](https://github.com/ithiria894/awesome-claude-code-hooks))
ему не нужны, и это тоже находка: **всё, что в них есть по безопасности, — это блокировки по
регулярным выражениям на именах файлов и командах, то есть тот же догоняющий подход, только на
девять кругов слома младше его собственного.** Ни одного структурного приёма в публичных подборках
не нашлось.

## D. Приёмы, дающие эффект сразу

**D1. Свод 21,4 КБ → путевые правила.** Инструкции можно разложить по `.claude/rules/*.md`, и
правило с frontmatter `paths:` **загружается только когда Claude читает файл, попадающий под
шаблон**. Правила без `paths` грузятся при старте с приоритетом `.claude/CLAUDE.md`.
Источник: [How Claude remembers your project](https://code.claude.com/docs/en/memory).
Важные оговорки: (1) `@path`-импорты контекст **не экономят** — импортированное разворачивается
при старте; (2) путевые правила и вложенные CLAUDE.md **не переинжектируются после компактизации**
(корневой CLAUDE.md — переинжектируется), то есть после `/compact` правило вернётся только когда
Claude снова тронет подходящий файл; (3) поддерживает ли `paths:` пользовательский
`~/.claude/rules/` — **док прямо не говорит, не подтверждено**, механика описана в разделе про
проектные правила. Для его случая это существенно: у него всё пользовательского скоупа.

Что из его 21,4 КБ реально не нужно в каждой сессии: правила пуша и PR (нужны, когда трогается git),
подсказки по инструментам (нужны по ситуации), таблица контуров. Что обязано остаться всегда:
язык ответов, идентичность и роли, границы и свобода, дома памяти.

**D2. Блочные HTML-комментарии в CLAUDE.md вырезаются до попадания в контекст** — заметки для себя
в своде не стоят токенов. В код-блоках сохраняются; при чтении файла инструментом Read видны.

**D3. `/context` показывает, что реально загрузилось** («Memory files»), `/doctor` с v2.1.206
предлагает срез свода — режет то, что выводится из кода, оставляет грабли и договорённости.
`InstructionsLoaded` хук журналирует, какие файлы инструкций загрузились и почему — прямой
инструмент под его долг «агент потерялся в инструкциях».

**D4. Границы словами (A2).** Даже без auto mode стоит запомнить сам приём: у Anthropic
сформулировано, что сказанная в разговоре граница держится до явного снятия, и **собственное
суждение агента о том, что условие выполнено, её не снимает**. Это ровно формулировка, которой не
хватает в его своде рядом с «окно прода открывает ОН».

**D5. Из его же кругов слома, но как переносимое правило.** Два приёма из [[tech-debt]] совпали с
тем, как устроены чужие структурные решения, и стоит записать это как норму, а не как случай:
«где можно проверять форму — проверять форму, а не искать подстроку» и «всё, что смотрит на текст,
смотрит на результат одной функции приведения». `srt` с его безусловными `denyWrite` и песочница с
защищённым списком настроек — это тот же приём, реализованный местом.

## Взять сейчас

1. **Включить встроенную песочницу Bash с auto-allow** (`sandbox.enabled: true`, начать с
   `filesystem.allowWrite` под `~/stack-vault`, `~/claude-stack`, `~/.claude`, `excludedCommands`
   для `docker *` и Go-CLI `gh`/`gcloud`/`terraform`). Это единственный найденный механизм, который
   закрывает класс «форма записи команды» целиком, и он **снимает трение, а не добавляет**:
   команды в границе исполняются без запроса. Ссылка: A1. Вес — средний (правка одного файла
   настроек плюс прогон на живой работе, обратимо одним ключом).
2. **`claude -p "/tidy"` по расписанию** — закрывает пункт долга «ночная рутина»: скиллы и команды
   штатно работают в `-p`. Обязательно с явным режимом разрешений (`dontAsk` или песочница),
   `--max-turns`, отчётом в файл, **без `--bare`** (иначе не сработают ни гейт, ни память). Ссылка: B1.
3. **`isolation: worktree` в персону `implementer`** — закрывает пункт долга про 36 worktree,
   размазанных по двум местам, свойством персоны. Ссылка: C. Вес — лёгкий.
4. **`maxTurns` и `memory` в персоны воркеров** — предел ходов на ночь и накопление граблей у
   `critic`/`verifier` между заходами. Ссылка: C. Вес — лёгкий.
5. **Разгрузить свод**: правила пуша/PR и подсказки по инструментам — в `.claude/rules/`, проверив
   на практике, работает ли `paths:` в пользовательском скоупе (доком не подтверждено). Блочные
   HTML-комментарии — бесплатно. Ссылка: D1, D2. Вес — средний.
6. **Хук `ConfigChange`** — блокировать изменение файлов конфигурации в сессии там, куда песочница
   не достаёт. Ссылка: C. Вес — лёгкий.
7. **Записать в норму формулировку про границы словами** (D4) и два переносимых правила из своих
   кругов (D5) — это не механизм, а текст, но он ровно про то место, где норма сейчас молчит.

## Не брать

1. **Auto mode как замену гейту — нет; как второй слой — да, но не первым шагом.** 17 % пропусков
   на реальных «переусердствовал» по их же измерениям, вероятностный, стоит токенов и задержки на
   каждую shell-команду, и при входе отбрасывает семь его широких allow-правил. Сначала песочница
   (детерминированная граница), потом решение про классификатор. Ссылка: A2.
2. **`@anthropic-ai/sandbox-runtime` — не сейчас.** Единственное, что накрывает MCP и хуки, но
   beta research preview с меняющимся форматом конфигурации под контуром, где он работает каждый
   день. Пересмотреть, когда уйдёт preview. Ссылка: A3.
3. **Контейнер, dev container, VM — нет.** Отказ 26.07 подтверждён по существу: они требуют Docker
   и переносят внутрь всё, включая MCP, `ssh-manager` и Keychain, и это ровно то трение, которое
   велено убрать. Плюс отдельная причина: `--dangerously-skip-permissions` отказывается стартовать
   от root, а под изоляцией он ему и не нужен.
4. **Чекпойнты `/rewind` как механизм откота для воркеров — нет.** Док прямо: правки субагентов
   вне чекпойнтов, изменения bash-команд не отслеживаются. Его схема «ветка + PR + мерж руками»
   надёжнее. Ссылка: B2.
5. **Облачные routines для ночной рутины стека — нет.** Не видят локальные файлы, MCP и серверы;
   ограничение из [[tech-debt]] за этот заход не опровергнуто. Ссылка: B3.
6. **`--bare` в ночных прогонах — нет, никогда.** Отключает хуки, MCP, память и CLAUDE.md, то есть
   ночь прошла бы без гейта и без журнала. Знать про него надо ровно чтобы не включить. Ссылка: B1.
7. **Публичные сборники хуков — нет.** Проверено три: всё по безопасности — блокировки регулярками
   по именам файлов и командам, то есть его же догоняющий подход на девять кругов младше.
8. **Forced command в `authorized_keys` — не сейчас, но записать.** Единственный честный
   структурный ответ для ssh-половины (392 проверки), и он на сервере, а не в агенте: значит
   требует его ОК на изменение сервера, а на серверах заказчика может быть недоступен. Ссылка: A5.

## Что осталось непроверенным

- Поддерживает ли `paths:` frontmatter пользовательский `~/.claude/rules/` — доком не сказано,
  проверяется только опытом.
- Дата открытия research preview для routines (вторичный источник называет 14.04.2026).
- Дата первого релиза `sandbox-runtime`.
- Совместимость песочницы с `ssh-manager` и `basic-memory` конкретно — в доке названы только
  `docker`, `watchman`, Go-CLI и Apple Events; MCP-серверы под песочницу Bash не попадают вовсе,
  значит вопрос стоит только про их stdio-запуск.
- Механизма отката половины применённой необратимой операции не нашлось ни у кого. Это результат
  поиска, а не отсутствие поиска.
