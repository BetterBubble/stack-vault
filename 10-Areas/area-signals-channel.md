# Канал сигналов

Адресная очередь межсессионных событий: отдельные окна-роли не видят друг друга, и канал — то, что
переносит между ними «есть событие, требующее твоего внимания» плюс ссылку на заметку с
содержанием. Текущее поколение — **v4** (с 25.07.2026).

**Принцип области:** доска — это память, канал — транспорт. Транспорт не заменяет память ни при
каком своём качестве, поэтому содержание всегда в заметке, а в сигнале — суть и ссылка.

## Как устроено сейчас

| Что | Где | Роль |
|---|---|---|
| `signal-send.sh` | `~/.claude/hooks/` | отправка: id под локом, публикация атомарна (`.tmp/` → `mv`) |
| `signal-watch.sh` | `~/.claude/hooks/` | процесс монитора: опрос inbox раз в секунду, вывод — событие в чат |
| `signal-status.sh` | `~/.claude/hooks/` | что в очереди + **вооружён ли монитор** (проверяется всегда) |
| `stop-reminder.sh` | `~/.claude/hooks/` | `Stop`-хук: не отпускает ход, если есть неразобранные сигналы |
| `role-register.sh` / `session-end.sh` | `~/.claude/hooks/` | адресация: строка роли в `~/.claude/.role-registry` |
| очередь | `$AGENT_VAULT/00-Board/signals/<роль>/inbox/` → `seen/` | один сигнал = один файл `sig-NNNNNN.json` |

Приём вооружает **агент**, а не оболочка — `Monitor` это инструмент сессии, хуком его не поставить:

```
Monitor({command: "bash ~/.claude/hooks/signal-watch.sh <своя-роль>",
         description: "сигналы to:<своя-роль>", persistent: true, timeout_ms: 3600000})
```

Ключевые свойства: id **монотонный по всему каналу** (счётчик `signals/.seq`, выдача под
mkdir-локом), тело **≤400 символов** (превышение — отказ отправки, не обрезка), `from` берётся из
реестра по `CLAUDE_CODE_SESSION_ID`.

## Почему так

- **Пробуждение через `Monitor`, а не через файловый watcher** — [[adr-cross-session-channel-not-native]].
  Сессия Claude Code действует только во время своего хода; простаивающая сессия файлы не опрашивает.
  У `Monitor` собственный процесс, а его вывод — событие в чате, то есть пробуждение за ≈1 с.
- **Agent Teams как транспорт запрещены** (решение Президента 25.07, там же в ADR): тиммейты живут
  внутри процесса лида, умирают вместе с ним, `/resume` их не восстанавливает. Разрешённая
  область — слой воркеров ВНУТРИ сессии.
- **Файл на сигнал, а не общая очередь в одном файле.** Получатель ловит появление файла событием, а
  не перечитывает общий файл, и конкуренции за один файл нет.
- **Выдача id под локом, а не «файлы атомарны, и так сойдёт».** Коллизия id = молча затёртый сигнал.
  Это нашёл `critic`, воспроизводя отказы: 8 одновременных отправок давали 3 файла, 5 сигналов
  исчезали молча, и все 8 рапортовали успех.
- **`✉️` подтверждает запись, а не доставку.** Подтверждений доставки канал не даёт ни в какой форме —
  и это сказано явно, чтобы на них не начали полагаться.

## Известные грабли

- **Монитор-сирота — самый дорогой случай.** Сессия умерла, процесс жив: он продолжает вычерпывать
  inbox своей роли в `seen/`, а будить некого — сигналы «доставлены» в никуда. Это ровно та потеря,
  из-за которой умер v3. Поиск: `pgrep -fl 'signal-watch\.sh'`, сверить с живыми окнами.
- **Смена адреса — два шага, не один.** `role-register.sh lead-qa` меняет только строку в реестре;
  старый монитор продолжает слушать старый адрес. Гасить: `pkill -f "signal-watch.sh <роль>$"` —
  **якорь `$` обязателен**, иначе `signal-watch.sh lead` совпадёт и с `lead-qa`.
- **Два окна с одним адресом получают КАЖДЫЙ сигнал оба** (воспроизведено). Перенос в `seen/`
  удаётся одному, второй печатает `⚠️`. Последствие не косметическое: два лида побегут делать одно
  и то же.
- **`timeout_ms` — обязательное поле схемы `Monitor`** (минимум 1000, при `persistent: true`
  игнорируется). Сниппеты вооружения без него не проходят валидацию — из-за этого вооружение канала
  было сломано **во всех восьми местах** сразу, при том что сам механизм был проверен: тестовый
  вызов поле содержал, а инструкция для ролей — нет.
- **Разные `$AGENT_VAULT` в двух окнах = два разных канала** при симптоме «сигнал не дошёл». Первый
  шаг диагностики — `echo $AGENT_VAULT` в обоих окнах.
- **Пустой inbox — это норма, а не улика:** при здоровом канале монитор вычерпывает его за ≈1 с.
- **Легаси-имена отличаются одной буквой** (`signals-send.sh` vs `signal-send.sh`), и разрешённым в
  allow-правилах раньше был именно легаси-путь, писавший в замороженный `_signals.md`. Агент шёл по
  разрешённой дороге, и сигнал не доезжал **никогда**.
- **Флаг исполняемости обязателен:** `role-register.sh` дёргает `signal-status.sh` напрямую, без
  флага это молчаливый `exit 126`. Доктор проверяет ВСЕ `hooks/*.sh`, а не только зарегистрированные.
- **`stop-reminder.sh` имеет принципиальный предел:** он стреляет только в момент завершения хода.
  У роли, которая уже отдала ход и простаивает, второго шанса нет — а это буквально тот сценарий,
  ради которого затевался v4.

## Как проверить, что живо

```bash
bash ~/.claude/hooks/signal-status.sh        # молчит, когда всё в порядке
pgrep -fl 'signal-watch\.sh'                 # сколько мониторов и на какие роли
bash ~/.claude/hooks/stack-doctor.sh         # разрывы и дубли id, копящиеся очереди, сироты
```

Норма: монитор ровно один на роль, очередь пуста, полная тишина от `signal-status.sh`.

## Границы

Канал **не хранит состояние** и не даёт ACK. Ждать ответ в цикле запрещено: отправил — продолжай
работу или припаркуй состояние на доске. **Писать в канал имеют право только сессии-роли** — воркер
живёт внутри сессии своего лида и придёт как `from:<роль лида>`, атрибуция соврёт.
