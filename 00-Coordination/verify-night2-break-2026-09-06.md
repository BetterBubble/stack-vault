# Критик-1: сломанное и лишнее в ночи 06.09 (проверено воспроизведением)

Метод: не чтение, а прогон. Каждая находка — команда и вывод. Проверялись коммиты ночи в
`~/claude-stack` (6a77201…) и `~/.claude` (b69259a…). Ранжировано: критика → высокое → среднее →
враньё в тексте → лишнее. Что ПРОШЛО пробы — в конце, честно.

## КРИТИКА — ломает защиту или работу

### 1. SENT-периметр снимается git'ом, mv и chmod — guard пропускает
- **Что сломано:** запись в часовых закрыта (12/12 проб deny), но снять часового БЕЗ записи можно.
  Пробы payload'ом через сам `guard.sh` (AGENT_ROLE=lead, GUARD_TEST_RUN=1):
  `mv ~/.claude/hooks/guard.sh /tmp/…` → **allow**; `git -C ~/.claude checkout -- hooks/guard.sh` →
  **allow**; `git -C ~/.claude reset --hard HEAD~3` → **allow** (откат гейта на старую, слабую
  версию); `git -C ~/.claude stash` → **allow**; `chmod 000 guard.sh` → **allow** (нечитаемый хук =
  хук не исполнился). `git` стоит в белом списке READERS — а он умеет переписывать рабочее дерево.
- **Чем доказано:** probe-скрипт `probe-sent2.sh` (scratchpad), вывод: SENT-13 allow, SENT-15 allow,
  SENT-16 allow, SENT-17 allow, SENT-18 allow. Для контраста: redirect/awk/dd/rsync/install/
  truncate/cp/python/ruby — все deny, чтение (grep, bash -n) — allow, как задумано.
- **Починка одной строкой:** в клаузе с путём часового считать записью также `mv|ln|chmod|chown` и
  `git` с глаголами `checkout|restore|reset|stash|clean|apply` (git с `log|diff|show|status|rev-parse`
  оставить чтением).

### 2. GRANT-WRITE: запрет запуска обходится тремя формами
- **Что сломано:** прямой `bash grant-write.sh` — deny, но `env bash …/grant-write.sh` → **allow**,
  `cat …/grant-write.sh | bash` → **allow**, `cp …/grant-write.sh /tmp/gw.sh && bash /tmp/gw.sh` →
  **allow** (копирование ИЗ периметра — «бэкап», запуск копии — уже не часовой). Барьер
  «окно записи открывает только человек» (решение 16.08) держится на первой форме запуска.
- **Чем доказано:** пробы GW-1…GW-5 через guard.sh: deny, allow, allow, allow, allow.
- **Починка одной строкой:** признак исполнения расширить префиксами `env|nohup|setsid|command|xargs`
  и формой «шелл читает stdin из клаузы с часовым» (`… | bash`, `bash < …`); копию-и-запуск честно
  назвать незакрываемой Bash-правилом и перенести барьер внутрь самого grant-write.sh (проверка
  «запущен человеком»: наличие TTY у родителя — агентские Bash без TTY).

### 3. tg-send.sh: длинная строка ломает отправку, а фейл прячется за rc=0
- **Что сломано:** (а) нарезка awk режет только ПО границам строк — одна строка 9000 символов даёт
  чанк 9000 (API-лимит 4096, отклонит) плюс ПУСТОЕ сообщение перед ним (тоже отклонит: печатается
  пустой `buf`); (б) `exit 1` при фейле чанка живёт в subshell пайпа — скрипт доходит до финального
  `exit 0`: «tg-send: чанк не отправлен» в stderr, а **rc=0**; (в) у curl нет `--max-time` — при
  зависшей сети виснет вызвавший (watchdog-таймер, session-start-хук; доктор сам варнит, что у
  хуков дефолтный timeout 600 с).
- **Чем доказано:** стаб curl + фейковый HOME: строка 9000 симв. → `CHUNK len=0` и `CHUNK len=9000`,
  rc=0; стаб с `"ok":false` → строка ошибки в stderr и **rc=0**. Кавычки/`$`/бэктики — прошли
  (--data-urlencode отрабатывает), пустой текст — честный rc=1.
- **Починка одной строкой:** в awk добить нарезку длинной строки посимвольно (substr в цикле, чанк
  никогда не пустой), после пайпа `|| exit 1`, к curl `--max-time 20`.

### 4. tg-bridge: незаполненный TG_TOPIC_PULT превращает General в пульт ГД
- **Что сломано:** `thread = msg.get("message_thread_id") or 0`, `T_PULT = int(env.get(...) or 0)` —
  пока топики не вписаны (или строка пуста), T_PULT=0 и ЛЮБОЕ сообщение владельца в General
  (thread=0) уезжает командой в tmux-окно ГД. Ровно сценарий «утром вставил токен, запустил мост,
  setup ещё не прогнал». На сервере мост уже `enabled` (пока inactive) — окно ошибки реальное.
- **Чем доказано:** симуляция строк 99–101: `route(None, T_PULT=0, ROUTES={})` → `work:main`.
- **Починка одной строкой:** `window = GD_WINDOW if (T_PULT and thread == T_PULT) else ROUTES.get(thread)`.

### 5. waiting-queue → TG: в «Ждёт меня» уходит мусор из YAML-шапки и подсказок
- **Что сломано:** дельта собирается как `grep -E '^- ' "$OUT"` по ВСЕМУ файлу — в топик уехали
  `- board`, `- queue` (теги YAML-шапки) и строка раздела «Похоже на ожидание, но маркера нет»,
  который сам файл называет «это НЕ очередь». Громкий топик засоряется с первого же прогона.
- **Чем доказано:** живой прогон на тестовом vault (стаб tg-send): в TG ушло 4 «развилки», из них
  настоящая одна; `- board`, `- queue` и подсказка без маркера — там же. Второй прогон — дельта
  пустая, 0 строк (эта часть работает).
- **Починка одной строкой:** брать строки только из секции очереди:
  `awk '/^## Ждёт решения/,/^## /' "$OUT" | grep '^- '`.

## ВЫСОКОЕ

### 6. gate-check слеп к секрету в промежуточном коммите
- **Что сломано:** «нет похожего на секрет» смотрит `git diff base...HEAD` — кумулятивный итог.
  Секрет, закоммиченный и убранный следующим коммитом, в истории ветки ЕСТЬ (уедет с пушем),
  а гейт говорит «чисто».
- **Чем доказано:** репо в scratchpad: коммит с `ghp_…`-токеном + коммит «fix: token from env» →
  `✔ нет похожего на секрет … чисто`, «НАРУШЕНИЙ НЕТ»; `git show feat~1:cfg.py` — токен на месте.
- **Починка одной строкой:** гонять leak_re по `git log -p %s..HEAD` (добавленные строки всех
  коммитов), а не по итоговому диффу.

### 7. Дрифт-чек доктора: съезд строк + совет, уничтожающий работу
- **Что сломано:** (а) два `rev-parse` в одном ssh разбираются позиционно (`sed -n 1p/2p`) — если
  первого репо на сервере нет/не ответил, head `.claude` приписывается `claude-stack`, а `.claude`
  считается пустым; (б) чек не различает «сервер отстал» и «сервер ВПЕРЕДИ»: прямо сейчас
  server/claude-stack на `cca0bfc` — на 2 коммита ВПЕРЕДИ мака (`cca0bfc`, `d680bde` есть только
  там), и совет «доставить бандлом: … + fetch/reset» стёр бы их.
- **Чем доказано:** симуляция односрочного ответа (head уехал в чужую переменную — вывод в пробе);
  `ssh stack git -C ~/claude-stack log --oneline -3` против локального лога: сервер впереди.
- **Починка одной строкой:** метить строки на сервере (`echo CS=$(git … rev-parse HEAD)` /
  `echo CC=…`) и при расхождении сначала `git fetch` + `rev-list --left-right --count` — «отстал»
  и «впереди» — разные диагнозы с разными советами.

### 8. tg-bridge: многострочное сообщение режется на отдельные вводы
- **Что сломано:** `send-keys -l` передаёт LF литерально, а в интерактивном prompt LF = submit.
  Сообщение из двух абзацев: первый уходит командой (с префиксом `[tg:…]`), второй вводится следом
  отдельно и БЕЗ префикса — попадает уже работающей сессии как посторонний ввод.
- **Чем доказано:** tmux-проба: `send-keys -l 'строка один\nстрока два'` → приёмник получил ДВА
  отдельных ввода (строки 1 и 2 в `cat -n`).
- **Починка одной строкой:** в `to_tmux` заменить `text = " ".join(text.split("\n"))` (или слать
  через bracketed paste), прежде чем send-keys.

### 9. tg-bridge: метка топика — по рангу, ответ роли уйдёт не в тот топик
- **Что сломано:** `topic_key` вычисляется как порядковый номер топика в `sorted(ROUTES)`, а не по
  соответствию `TG_TOPIC_TASKn`. Если в ROUTES замаплена только «Задача 2», её сообщение помечается
  `[tg:task1]` — роль по контракту ответит `tg-send task1`, и ответ ляжет в топик «Задача 1».
- **Чем доказано:** симуляция строк 129–130: ROUTES={555: win}, 555=TASK2 → метка `task1`.
- **Починка одной строкой:** строить `{int(env[f"TG_TOPIC_TASK{i}"]): f"task{i}"}` из env и брать
  метку оттуда.

### 10. voice-response: ответы-списки не озвучиваются вовсе
- **Что сломано:** фильтр не снимает ведущий `-`, а маркдаун-список — самый частый формат финального
  ответа. `say -v Milena "$text"` читает `- пункт…` как опции: «invalid option», rc=1, тишина;
  argparse edge-tts о ведущем дефисе спотыкается так же. Голос «включён, но молчит» — необъяснимо
  для пользователя.
- **Чем доказано:** `say -v Milena -o x.aiff "- первый пункт готов"` → invalid option, rc=1;
  с `--` перед текстом → rc=0, файл 55 КБ. Фильтр python пропускает текст с ведущим «- » (проба).
- **Починка одной строкой:** `say -v Milena -- "$text"` и в фильтре `t = re.sub(r"^[-–—•\s]+", "", t)`.

## СРЕДНЕЕ

### 11. waiting-queue: дельта теряется при неудачной отправке; первый прогон — вся очередь скопом
`bash "$TGS" … || true` и следом безусловный `printf '%s' "$cur" > "$SENT"` — фейл отправки
(сеть, лимит) записывает пункты как «отправленные», они не уйдут уже никогда. Плюс при первом
включении tg дельта = вся очередь целиком. Починка: писать SENT только при rc=0 tg-send (после
починки №3, иначе rc всегда 0).

### 12. watchdog: свежее окно роли — «мёртвое» без 10-минутной форы
Строки 90–92: штампа нет И в панели не claude → в `_dead-roles.md` и в маячок сразу. Окно, поднятое
минуту назад (claude ещё стартует), даёт ложный алерт — в том числе в TG (переход ловится по
отсутствию ALERT-файла). Починка: при отсутствии штампа ставить его и ждать следующего прогона.
Сам скрипт: `bash -n` чист, `reasons=()` при `set -u` безопасен даже на bash 3.2 (проверено),
`${reasons[@]}` раскрывается только под гардом непустоты.

### 13. tg-setup: дружелюбные ошибки — мёртвый код, повторный прогон при живом мосте — traceback
Telegram отвечает на ошибки HTTP 400/409, urllib кидает HTTPError ДО разбора json — ветки
`if not r.get("ok")` («у бота есть право Manage Topics?») недостижимы, человек утром получит голый
traceback. Тот же traceback — при прогоне setup, пока мост держит getUpdates (409 Conflict).
Группа без сообщения владельца — обработана честно (exit с инструкцией). Починка: обернуть `api()`
в try/except HTTPError с чтением `e.read()`. Заодно: стартовый пропуск хвоста в мосте читает один
батч (100 апдейтов) — хвост длиннее ста всё-таки исполнится.

## НОРМА ВРЁТ О МЕХАНИЗМЕ (их же собственный класс)

### 14. voice-response: комментарий «flock:» — а в коде mkdir-лок
Шапка обещает flock, механизм — `mkdir "$LOCK"` со снятием по возрасту. По правилу стека «норма
обязана называть свой настоящий механизм». Починка: слово в комментарии.

### 15. gate-check: «GATE_ACK_UNCHECKED … на вердикт не влияет» — влияет
Проба: без входов rc=3 (честно, как заявлено); с `GATE_ACK_UNCHECKED='скоуп,метрики,гейт приёмки
материалов,апрув плана'` → **rc=0** при нуле выполненных доп-проверок. ACK по замыслу и должен
снимать блокировку — но печатаемая фраза «на вердикт не влияет» ложна, и ничто не мешает ночному
пайплайну самому себе выставить ACK. Починка: фразу исправить («снимает блокировку, но остаётся в
отчёте»), в autonomous-feature запретить ACK для деплойных прогонов.

## ЛИШНЕЕ / ДУБЛИ

- **Детект мёртвых ролей теперь в двух местах с разными источниками правды:** watchdog смотрит
  tmux-панели (`pane_current_command`), доктор — pid'ы реестра. Разойдутся — будут спорить друг с
  другом в двух разных файлах. Достаточно одного механизма (watchdog), доктору — читать его файл.
- **Нарезка 4000 реализована дважды:** `tg-send.sh` (awk по строкам) и `say()` в tg-bridge
  (срез по символам). Уже разошлись поведением. Мосту хватило бы вызова tg-send.
- **teammate-idle** дублирует правило персоны текстом — но это осознанная страховка «текст
  забывается», к ней претензий нет; пробы (5 форм payload) отработали как заявлено.
