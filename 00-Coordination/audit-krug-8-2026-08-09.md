# Аудит стека круг 8 — находки ревизора-ломателя 2026-08-09

Только чтение, кроме этого файла; все пробы — в песочнице скратчпада (подменённый `HOME`,
одноразовые репозитории и vault, песочная кнопка `AGENTS_OFF` в песочном `.claude`). Живые кнопки,
реестр, память и git-головы не тронуты. На серверы не ходил. Области круга: обе стороны git-белого
списка круга 7 · правило PUSH (двухуровневые формы) · `waiting-queue.sh` · `session-end.sh` ·
новые области — `stack-doctor.sh` (память/досье/направления/git-состояние), `agent-company.md`,
`memory-protocol.md`, `commands/*.md`.

**Пустого круга не вышло.** Мутирующая сторона git-стопа держит железно (единичная команда — любая
мутация ловится, включая все обходы круга 7). Но у той же починки **вскрылась дыра в другую
сторону: составная строка обходит стоп** (находка 1), и **симметрично — стоп рубит обычные читающие
git-команды** вопреки собственному обещанию (находка 2). Плюс три расхождения «документ против кода»
в двух неприкосновенных доках.

## 1. Полный стоп `AGENTS_OFF` обходится составной строкой: читающая git-подкоманда ПЕРВОЙ открывает мутацию ВТОРОЙ

**КЛАСС:** дыра гейта, худшее направление (запись мимо аварийного стопа). Тот же инвариант, что
чинил круг 7, снова ложен — теперь из-за того, что белый список судит ТОЛЬКО первую git-клаузу
строки.

**ЧТО.** Под `AGENTS_OFF` для Bash (`guard.sh:987-1006`) подкоманда берётся через `git_sub(cmd)`
(`guard.sh:194-201`), а он — `re.search`, то есть находит ПЕРВОЕ вхождение `git`. Если первая
подкоманда читающая (`status`/`log`/`rev-parse`/`config --get`), ставится `git_read=True`,
`git_hit=False`. Вторая, мутирующая git-команда в той же строке не разбирается вовсе, а
чёрный список `GIT_MUTATE` применяется только под условием `not has_git` (`guard.sh:1005`) — и раз
`has_git` уже True, он не срабатывает. Итог: `git <чтение> && git <мутация>` проходит стоп.

**ВОСПРОИЗВЕДЕНИЕ** (песочный `HOME` с `AGENTS_OFF`, роль `lead`, настоящий `guard.sh`):
```
AGENTS_OFF: git status && git commit -m wip                  => ALLOW  ← коммит мимо стопа
AGENTS_OFF: git log && git config user.name h                => ALLOW
AGENTS_OFF: git status; git push origin main                 => ALLOW  (в личном/чужом репо — мимо и стопа, и PUSH)
AGENTS_OFF: git status && git notes add -m x HEAD            => ALLOW
AGENTS_OFF: git rev-parse HEAD && git subtree push … main    => ALLOW
AGENTS_OFF: git rev-parse HEAD && git config core.hooksPath /tmp/evil  => ALLOW  ← класс RCE
AGENTS_OFF: git log -1 && git config alias.x '!sh -c payload'          => ALLOW  ← класс RCE
контроль (одиночные — ловятся):
AGENTS_OFF: git commit -m wip                                => DENY
AGENTS_OFF: git config core.hooksPath /tmp/h                 => DENY
AGENTS_OFF: git subtree push --prefix=dist origin main       => DENY
```
Прямой вывод `guard.sh` подтверждает: `git status && git commit -m wip` → пустой ответ (ALLOW);
одиночный `git commit -m wip` → JSON `permissionDecision:"deny"`.

**ПОСЛЕДСТВИЕ.** Инвариант хука («ЛЮБАЯ запись запрещена всем ролям… мутирующий git») снова ложен:
достаточно приписать читающую git-подкоманду перед мутацией. `git log && git commit` — не экзотика,
а обычная составная форма; `git rev-parse HEAD && git config core.hooksPath …` под стопом задаёт
исполнение произвольного кода при следующей git-операции. Единственный уцелевший бэкстоп — правило
PUSH, и то лишь для пуша и лишь в рабочем репозитории; коммит, `config`, `notes`, `subtree push`
в личном/чужом репо не ловит ничего.

**ЧТО ЧИНИТЬ.** Судить КАЖДУЮ git-клаузу, а не первую — ровно как это уже делает правило PUSH
(`guard.sh:1385` разбивает по `(?<!\\)[|;&]+|\n`). Прогнать `git_sub`+белый список по всем клаузам
строки, а не по первому совпадению; либо снять условие `not has_git` у `GIT_MUTATE`, чтобы чёрный
список ловил вторую мутацию (но это возвращает отставание перечня — правильнее клаузы). Юнит доктора:
`git status && git commit` под стопом обязан дать DENY.

## 2. Тот же белый список рубит обычные ЧИТАЮЩИЕ git-команды под стопом — вопреки его же обещанию «чтение разрешено»

**КЛАСС:** ложный отказ на аварийном стопе — бьёт по человеку в момент разбора аварии. Обратная
сторона находки 1: перечень `GIT_READONLY_SUB` (`guard.sh:187-192`) уже, чем реальный набор чтений.

**ЧТО.** Стоп печатает «Чтение, поиск и анализ разрешены», но под ним отказывают штатные читающие
формы, которых нет в белом списке: `branch`, `remote`, `tag`, `stash`, `worktree`, `for-each-ref`,
`symbolic-ref`. `config` получил разбор по флагам (`--get/--list` читают — `guard.sh:998`), а эти
подкоманды — нет, хотя их читающие формы столь же однозначны. Причём **сам guard.sh в другом месте
уже знает**, что `git branch -a` — чтение: SSH-классификатор (`guard.sh:543,778`) отличает
`git branch <имя>` (создаёт) от `git branch -a` (перечисляет), и в доктора есть зелёный тест
`СЛОМ-2 Д3-обратно: git branch -a перечисляет => allow` (`stack-doctor.sh:1342`). То есть под стопом
хук отрицает то, что сам классифицирует как чтение.

**ВОСПРОИЗВЕДЕНИЕ** (песочный `AGENTS_OFF`, роль `lead`):
```
git branch -a       => DENY      git remote -v      => DENY
git stash list      => DENY      git worktree list  => DENY
git for-each-ref    => DENY      git symbolic-ref -q HEAD => DENY
git tag -l          => DENY      git config user.email (без --get) => DENY
контроль (в белом списке): git status/log/diff/show/rev-parse/reflog/describe/cat-file => ALLOW
```

**ПОСЛЕДСТВИЕ.** Человек, разбирающийся в замороженной аварии (ровно сценарий, ради которого стоп
обещает чтение), не может посмотреть ветки, remote, стэш и worktree'ы. Это не гипотетика: `git
branch`, `git remote -v`, `git stash list`, `git worktree list` — первое, что смотрят при разборе
git-состояния. Асимметрия с `config` показывает, что это недосмотр, а не осознанный выбор: если бы
«лишний отказ» был приемлем для этих подкоманд, `config` не получил бы исключения.

**ЧТО ЧИНИТЬ.** Достроить белый список читающими подкомандами (`for-each-ref`, `show-ref`,
`symbolic-ref -q`) и разобрать по флагам двуликие группы так же, как `config`: `branch`/`tag`
без позиционного имени и с `-l/--list/-a/--show-current/-v` — чтение; `remote` с `-v/get-url/show`
(без `add/set-url/remove/rename`) — чтение; `stash list/show` — чтение; `worktree list` — чтение.
Общий принцип уже отработан в SSH-классификаторе того же файла — свести к одному разбору.

**КЛАСС:** правило неприкосновенного дока противоречит коду; норма описывает несуществующий барьер.

**ЧТО.** В диаграмме пайплайна (`agent-company.md:106`) шаг деплоя: «🎯 деплой по runbook (бэкап →
deploy → verify) — **только внутри открытого окна автономии**». Но окно автономии вырезано целиком

менять прод — не окно. Файл обновлялся сегодня (`updated: 2026-08-09 04:55`), но эта строка осталась.

**ВОСПРОИЗВЕДЕНИЕ.** `grep -n "окн" agent-company.md` → строка 106 несёт «открытого окна автономии»
как условие деплоя; `grep -n "окна автономии больше НЕТ" guard.sh` и `grep "вырезано" working-model.md`

**ПОСЛЕДСТВИЕ.** Канонический дизайн — то, по чему сверяются роли и `critic` — обещает на самом

на деле защиту держат другие механизмы, а «окно» ввело бы в заблуждение при разборе, «что не пустило
деплой» или «что должно было не пустить».

**ЧТО ЧИНИТЬ.** Переписать шаг деплоя в диаграмме на действующие барьеры (обе кнопки стопа + устный
ОК Президента + воркер прод не меняет), убрать «окно автономии». Правится только вместе с Президентом
(неприкосновенный файл) — вынести пунктом на решение.

## 4. `memory-protocol.md` §10: две секции досье НАПРАВЛЕНИЯ заявлены «кодом не проверяются вовсе» — а доктор их проверяет

**КЛАСС:** утверждение неприкосновенного дока о механизме противоречит коду; §10 объявляет себя
честной картой «что в коде, что на дисциплине» — и в этой точке ошибается.

**ЧТО.** `memory-protocol.md:331-333`: «**Две новые секции досье НАПРАВЛЕНИЯ** (`Боль направления`,
`Как поток устроен`) кодом **не проверяются вовсе** — они на дисциплине ГД». Но `stack-doctor.sh`
их проверяет: `NEED_NEW = ["Боль направления", "Как поток устроен"]` (`stack-doctor.sh:230`) и варн
при отсутствии — `warn "досье направлений без секций решения 29.07…"` (`stack-doctor.sh:256`).
Проверка направлений добавлена ПОСЛЕ последней правки регламента (`memory-protocol.md` — `updated:
2026-07-26`; комментарий доктора `stack-doctor.sh:218`: «Прежде доктор не смотрел на них вовсе»), то
есть док отстал и стал ложным.

**ВОСПРОИЗВЕДЕНИЕ.** `grep -n "Боль направления" stack-doctor.sh` → строки 230 и 256 (проверка есть).
`memory-protocol.md:331-333` утверждает обратное. §7 (`memory-protocol.md:239`) вдобавок обещает, что
§10 «честно перечислено, что уже в коде, а что держится на ГД» — обещание нарушено ровно здесь.

**ПОСЛЕДСТВИЕ.** Регламент, по которому работает вся память, занижает фактическое покрытие: роль,
доверяющая §10, считает секции направления делом дисциплины и может не среагировать на варн доктора
как на «нормальный» (доктор ведь «их не проверяет»). Направление ложное — код строже дока, не
слабее, — но неприкосновенный канон обязан описывать механизм точно.

**ЧТО ЧИНИТЬ.** Обновить §10: обе секции направления проверяются доктором как ВАРН (симметрично трём
секциям фичи). Правка регламента — только с Президентом; вынести пунктом на решение.

## Гипотезы (без полного воспроизведения либо низкой частоты)

- **`waiting-queue.sh`: маркер в HTML-комментарии и после РАЗНОТИПНОГО фенса утекает в очередь.**
  Проверка in-code переключается на строках `` ``` `` и `~~~` (`waiting-queue.sh:103`), но не знает
  HTML-комментариев и не различает тип фенса. На песочной доске: `<!-- @ЖДЁТ: … -->` → в очередь
  попал пункт «… --> » (с хвостом `-->`); блок, открытый `` ``` `` и «закрытый» `~~~`, оставил
  маркер после `~~~` видимым (по CommonMark он ещё внутри кода). Длинные фенсы (`` ```` ``, `~~~~`),
  info-string (`` ```python ``) и незакрытый фенс отработали ВЕРНО (маркер подавлен), настоящая
  развилка попала. Обе утечки — низкой частоты (документируют формат обычно обычным фенсом), тот же
  косметический класс, что хвост `\r`/` |` прежних кругов. Чинить: игнорировать строки в
  `<!-- … -->` и переключать in-code только парным типом фенса.
- **`session-end.sh`: на пути B журнала (когда нет `~/.claude/logs/`) в stderr течёт ошибка
  редиректа.** Запись detached-HEAD-следа (`session-end.sh:106-109`) — `printf >> logs/… 2>/dev/null
  || printf >> .claude/…`. Порядок редиректов: `>> файл` применяется РАНЬШЕ `2>/dev/null`, поэтому
  при отсутствии каталога `logs/` сообщение «No such file or directory» уходит на живой stderr, хотя
  `2>/dev/null` стоит именно чтобы его подавить. Данные не теряются — фолбэк (путь B) пишет в
  `~/.claude/session-end.log` (воспроизведено на песочном HOME без `logs/`). На живой машине
  `~/.claude/logs/` существует, путь A срабатывает, ошибки нет — поэтому гипотеза, а не находка.
  Чинить: `mkdir -p …/logs` перед записью либо порядок `2>/dev/null >> …`.

## Что проверил и нашёл исправным (туда не возвращаться)

- **Мутирующая сторона git-стопа держит железно (единичные команды).** Под песочным `AGENTS_OFF`
  DENY на все обходы круга 7 и сверх того: `config <set>` (вкл. `core.hooksPath`, `alias.x '!…'`),
  `notes add`, `replace`, `bundle create`, `subtree push/add`, `submodule add`, `update-ref`,
  `symbolic-ref HEAD <ref>`, `remote add/set-url`, `tag <имя>`, `branch <имя>`, `stash push`,
  `checkout -b`, `switch -c`, `restore`, `reset`, `clean`, а также пломбовое `fast-import`, `mktag`,
  `hash-object -w`, `write-tree`, `commit-tree`, `-c core.editor=… commit`. Незнакомая подкоманда под
  стопом → DENY (fail-closed работает). Дыра только в СОСТАВНОЙ строке — находка 1.
- **Правило PUSH — двухуровневые формы (починка круга 7 №2) держит.** Из рабочего репозитория:
  `git push origin main` → DENY; `git subtree push --prefix=dist origin main` → DENY; `git subtree
  push … origin feature/x` → ALLOW (доставка ветки); `git submodule foreach git push origin main` →
  DENY; `git push --mirror` → DENY; `git push origin HEAD:main` → DENY; доставка `git push origin
  feature/x` → ALLOW. Личный контур: `push origin main` и `push origin feature/x` → ALLOW.
- **`session-end.sh` (починка круга 7 №3) держит.** Обычная ветка с изменениями → авто-коммит создан;
  без изменений → пустого коммита нет; detached HEAD → коммита НЕТ, след записан. Журнал пути A на
  живой машине уже содержит записи detached-HEAD-скипов (`~/.claude/logs/session-end.log`); путь B
  срабатывает при отсутствии `logs/` (данные не теряются — см. гипотезу про stderr).
- **`waiting-queue.sh` — фенсы (частично).** Длинные фенсы (`` ```` ``, `~~~~`), info-string,
  незакрытый фенс подавляют маркер верно; настоящая развилка попадает. Утечки — только HTML-коммент
  и разнотипный фенс (гипотезы).
- **`stack-doctor.sh` — секции памяти/досье/направлений/git-состояния.** Проверки содержательны и
  проваливаются по делу: досье фич (8 секций провал + 3 варн + заглушки + done-at/overdue/staledone
  + блок «Для руководителя»), досье направлений (7 секций провал + 2 варн + статусы), `session-state`
  >8 КБ → bad, git-состояние репозиториев (нет remote → bad, >40 грязных → warn, неотправленные
  коммиты → warn), валидность `settings.json` и исполнимость/`bash -n` (вкл. системный `/bin/bash`)
  хуков. Проверок «которые не могут провалиться» в этих секциях не нашёл; каждая имеет разделяющий
  порог. (Расхождение §10↔доктор по секциям направления — находка 4, это дефект ДОКА, не проверки.)
