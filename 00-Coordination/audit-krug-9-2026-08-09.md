# Аудит стека круг 9 — находки ревизора-ломателя 2026-08-09

Только чтение, кроме этого файла; пробы гейта — в песочнице скратчпада (подменённый `HOME`,
одноразовый git-репозиторий, песочная кнопка полного стопа в песочном `.claude`, `GUARD_TEST_RUN=1`).
Живые кнопки, реестр, память и git-головы не тронуты. На серверы не ходил. Области круга: главная —
починки круга 8 в аварийном стопе (`guard.sh`, поклаузный разбор git); плюс новые — роли
`director`/`planner`/`stack`/`creator`, регламенты `signals.md`/`session-lifecycle.md`/`verify-checklist.md`/`serena-guide.md`,
непроверенные хуки.

**Пустого круга не вышло — две находки.** Починка круга 8 закрыла дыру со РАЗДЕЛИТЕЛЕМ
(`git status && git commit`), но **тот же дефект «судим только первую git-подкоманду» уцелел ВНУТРИ
одной клаузы**: две git в одной клаузе через подстановку `$(…)`, обратные кавычки, env-префикс или
`find -exec` — первая читает, вторая пишет мимо стопа (находка 1, худшее направление, класс RCE).
Плюс расхождение регламента с кодом: `signals.md` утверждает, что провал доктора по мониторам «не
попадает в код возврата», а он попадает (находка 2).

## 1. Аварийный стоп `AGENTS_OFF` обходится ДВУМЯ git В ОДНОЙ клаузе: первая читает — вторая пишет мимо стопа

**КЛАСС:** дыра гейта, худшее направление (запись мимо аварийного стопа, класс RCE). Ровно тот
инвариант, что чинили круги 7 и 8, снова ложен — теперь на уровне ОДНОЙ клаузы.

**ЧТО.** Круг 8 стал разбивать строку на клаузы (`guard.sh:1035`, `re.split(r"(?<!\\)[|;&]+|\n")`)
и судить каждую через `git_clause_writes` — это закрыло `git status && git commit`. Но
`git_clause_writes` (`guard.sh:226-240`) внутри клаузы вызывает `git_sub` (`guard.sh:217-224`), а
тот — `re.search`, то есть находит ТОЛЬКО ПЕРВУЮ подкоманду git в клаузе. Если в одной клаузе (без
шелл-разделителя `|;&\n` между ними) стоят два вызова git и первый — читающий, вердикт выносится по
первому, второй (мутирующий) не разбирается вовсе. Два git в одной клаузе — это обычные формы:
подстановка команд `$(git …)`, обратные кавычки `` `git …` ``, env-префикс `x=$(git …) git …`,
`find … -exec git … \; -exec git … \;` (внутри одной клаузы, `\;` разделителем не является —
`(?<!\\)` его не рвёт).

**ВОСПРОИЗВЕДЕНИЕ** (песочный `HOME` с нажатым полным стопом, роль `lead`, настоящий `guard.sh`,
cwd = песочный git-репо):
```
x=$(git log -1 --format=%H) git commit -m wip                     => ALLOW  ← коммит мимо стопа
x=$(git status) git config core.hooksPath /tmp/evil               => ALLOW  ← класс RCE (следующая git-операция исполнит чужой код)
x=`git log -1` git push origin main                               => ALLOW  (в личном/чужом репо — мимо стопа; PUSH держит отдельно только рабочий репо)
GIT_PAGER=$(git status) git commit --amend                        => ALLOW
find . -maxdepth 0 -exec git status \; -exec git commit -m wip \; => ALLOW  ← find выполнит обе exec
контроль (первая git пишет, либо не-git префикс):
x=$(pwd) git commit -m wip                                        => DENY
test -n "$(git rev-parse HEAD)" && git status || git commit       => DENY  (разделители рвут на клаузы — работает починка круга 8)
```
Все ALLOW-строки реально выполняют ДВЕ git-команды (проверено семантикой bash: env-префикс
`x=$(…) cmd` исполняет подстановку, затем `cmd`; `find` с двумя `-exec` выполняет обе на каждом
совпадении). `WRITE_VERB`, `INTERP` и `GIT_MUTATE` их не ловят: `commit`/`config`/`push` не глаголы
записи Bash; `GIT_MUTATE` применяется только при `not has_git` (`guard.sh:1042`), а `has_git` тут
True. Единственный судья — `git_hit`, и он False, потому что смотрит первую подкоманду.

**ПОСЛЕДСТВИЕ.** Инвариант хука («при `AGENTS_OFF` ЛЮБАЯ запись запрещена всем ролям», `guard.sh:1005`)
снова ложен: достаточно поставить читающую git-подкоманду ПЕРВОЙ в той же клаузе. Круг 8 закрыл эту
дыру для разделителей и в отчёте назвал `git status && git commit` «не экзотикой, обычной составной
формой» — подстановка команд и env-префикс столь же обычны, а `x=$(git status) git config
core.hooksPath …` под стопом задаёт исполнение произвольного кода при следующей git-операции.
Тот же корень («смотрим только первую подкоманду»), что уже дважды признавался дефектом, — не изжит,
а сдвинут на уровень глубже.

**ЧТО ЧИНИТЬ.** `git_clause_writes` обязан судить ВСЕ вхождения git в клаузе, а не первое. Вариант:
пройти по всем совпадениям `re.finditer(r"\bgit\b…")` в клаузе и вернуть True, если ЛЮБОЕ из них
пишет; либо (проще и надёжнее) снять условие `not has_git` у `GIT_MUTATE` (`guard.sh:1042`) — тогда
чёрный список поймает вторую мутацию, даже когда белый пропустил первую-читающую (ценой возврата
проблемы «перечень отстаёт», поэтому правильнее итерировать по всем git). Юнит доктора:
`x=$(git log -1) git commit` и `find . -exec git status \; -exec git commit \;` под стопом обязаны
дать DENY.

## 2. `signals.md`: провал доктора по мониторам заявлен «не попадает в код возврата» — а попадает (норма против кода)

**КЛАСС:** регламент противоречит коду; описывает несуществующий изъян доктора как действующий.
Область — регламент `signals.md`, который сам объявляет себя «единственным описанием кода канала и
обязан с ним совпадать» (`signals.md:18`).

**ЧТО.** `signals.md:142`: «`stack-doctor.sh` → `ПРОВАЛ мониторов на роль <роль>: N`. Читай вывод,
а не только последнюю строку: эта проверка печатает ПРОВАЛ, но **в итоговый счётчик и код возврата
доктора пока не попадает**, поэтому внизу может стоять «всё чисто»». Но в коде проверка
монитор-на-роль ровно одна (`stack-doctor.sh:789`) и печатает через `bad`, а
`bad() { FAIL=$((FAIL+1)); … }` (`stack-doctor.sh:35`) инкрементит `FAIL`; финал
(`stack-doctor.sh:2548-2552`): `FAIL>0` → печать «N провал(ов)» и `exit 1`, «всё чисто» не печатается
никогда при `FAIL>0`. То есть провал ПОПАДАЕТ и в счётчик, и в код возврата. Вдобавок расходится сам
текст сообщения: док обещает «ПРОВАЛ мониторов на роль `<роль>`: N», код печатает «ПРОВАЛ мониторов
на роль больше одного: `<роли>` — каждый сигнал придёт в оба окна…».

**ВОСПРОИЗВЕДЕНИЕ.** `grep -n "монитор" stack-doctor.sh` → единственная проверка на строке 789 через
`bad`; `sed -n '35p;2548,2552p' stack-doctor.sh` → `bad`→`FAIL++`→`exit 1`. `signals.md:141-142`
утверждает обратное. (Вторая половина п.141 — про `signal-status.sh` «⚠️ мониторов на роль N (должен
быть 1)» — коду СООТВЕТСТВУЕТ: `signal-status.sh:108`.)

**ПОСЛЕДСТВИЕ.** Регламент занижает надёжность доктора: он учит «не верь итоговой строке, „всё
чисто“ может скрывать провал по мониторам» — тогда как итоговая строка теперь честна (дубль монитора
даёт «N провал(ов)» и `exit 1`). Читающий либо перепроверяет вручную то, что доктор уже ловит, либо
переносит недоверие на код возврата доктора в целом. Слово «пока» в тексте показывает, что это был
временный изъян, который в коде закрыли, а в регламенте забыли снять.

**ЧТО ЧИНИТЬ.** Переписать `signals.md:142`: провал по мониторам печатается через `bad`, входит в
счётчик `FAIL` и даёт `exit 1` — итоговой строке доверять можно. Заодно привести цитату сообщения к
фактической («мониторов на роль больше одного: …»). Файл правится свободно (не из неприкосновенной
тройки).

## Что проверил и нашёл исправным (туда не возвращаться)

- **Аварийный стоп, мутирующая сторона — единичные и разделённые формы держат.** Под песочным
  полным стопом DENY на: `git commit`, `git config core.hooksPath …`, `git status && git commit`,
  `test … && git status || git commit`, `x=$(pwd) git commit`. Дыра только в ДВУХ git в ОДНОЙ клаузе
  (находка 1).
- **Аварийный стоп, читающая сторона — починка круга 8 держит, ложных отказов нет.** ALLOW на всех
  двуликих читающих формах: `git config --get user.email`, `git remote -v`, `git stash list`,
  `git submodule status`, `git notes list`, `git bisect log`, `git tag -l`, `git branch -a`,
  `git worktree list`, `git -c core.pager=cat log`. Обещание стопа «чтение разрешено» для git
  выполняется.
- **Правило PUSH двумя git в клаузе НЕ обманывается.** В отличие от `git_clause_writes`, PUSH ищет
  `GIT_PUSH_RE` по ВСЕЙ клаузе (`guard.sh:1422-1423`), а не по первой подкоманде — потому и форма
  «читающая git, затем `git push … main`» в рабочем репозитории ловилась бы. Дефект «первая
  подкоманда» локализован в стоп-классификаторе.
- **Легаси-шимы канала сигналов делегируют корректно.** `signals-send.sh` → `exec … signal-send.sh`,
  `signals-check.sh` → `exec … signal-status.sh` (оба маленькие, с явной пометкой «легаси-шим»).
  Не мёртвый код, а осознанная совместимость; `signals.md:54` их так и описывает.
- **Ссылки регламентов и ролей ведут в существующее.** Хуки из `roles/*.md`
  (`signal-send`/`signal-watch`/`signal-status`/`roles-free`/`stuck-check`/`open-lead`/`gate-check`/
  `stack-doctor`) существуют; `director.md:118` верно утверждает, что субагентов `creator`/`planner`
  нет (в `~/.claude/agents/` их дефиниций нет). `~/.claude/agent-memory/`, `gate-check.sh`,
  `autonomous-feature.js` (в `~/.claude/workflows/`) на месте. Битых ссылок не нашёл.
