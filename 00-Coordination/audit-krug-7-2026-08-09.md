# Аудит стека круг 7 — находки ревизора-ломателя 2026-08-09

Только чтение, кроме этого файла; все пробы — в песочнице скратчпада (подменённый `HOME`,
одноразовые репозитории и vault, песочная кнопка `AGENTS_OFF` в песочном `.claude`; живые кнопки,
реестр, память и git-головы не тронуты). На серверы не ходил. Области круга: пять починок круга 6 ·
правило PUSH целиком (мои новые формы) · `session-end.sh` · `secret.sh`.

**Все пять починок круга 6 держат** (перепроверены — см. «нашёл исправным»). Но пустого круга снова
не вышло: **три доказанных находки**, и первая — того же класса, что чинил круг 6 (узкий якорь /
закрытый перечень глаголов), только оставленного неисправленным для git.

## 1. Полный стоп `AGENTS_OFF` пропускает МУТИРУЮЩИЕ git-подкоманды: `git config`, `git notes`, `git replace`, `git bundle`, `git subtree` — перечень глаголов `GIT_MUTATE` привязан к слову СРАЗУ после `git`

**КЛАСС:** дыра гейта, худшее направление (запись мимо аварийного стопа). Тот же корень, что
находка 1 круга 6 (`iva-write`): закрытый перечень с узким якорем. Круг 6 починил его для имён MCP
(`(?:^|_)verb`), но `GIT_MUTATE` и `GIT_PUSH_RE` остались с якорем «глагол сразу после `git` и
глобальных флагов». Встроенные подкоманды, которых нет в перечне, и двухуровневые формы
`git <группа> <глагол>` проходят полный стоп.

**ЧТО.** Под `AGENTS_OFF` для Bash проверяются `WRITE_VERB`, `GIT_MUTATE` и `INTERP`
(`guard.sh:943-952`). `GIT_MUTATE` (`guard.sh:178-181`) — это `git\s+(?:-\S+\s+|--\S+=\S+\s+)*(?:push|commit|merge|…)`:
между `git` и глаголом допускаются только ФЛАГИ. Поэтому:
- **`git subtree push` / `git subtree add`** — слово `subtree` не флаг, `(?:…)*` матчит ноль, дальше
  ждётся `push|commit|…`, а стоит `subtree` → не совпало. Проходит.
- **`git config`, `git notes`, `git replace`, `git bundle`** — этих глаголов в перечне нет вовсе.
  Проходят, хотя каждый меняет состояние (config, refs/notes, refs/replace, файл на диске).

**ВОСПРОИЗВЕДЕНИЕ** (песочный `HOME` с `AGENTS_OFF`, роль `lead`, через настоящий `guard.sh`):
```
AGENTS_OFF: git subtree push --prefix=dist origin main => ALLOW   ← пуш в main мимо ДВУХ стопов
AGENTS_OFF: git subtree add --prefix=vendor origin main => ALLOW
AGENTS_OFF: git config user.name hacker               => ALLOW   ← мутация config
AGENTS_OFF: git notes add -m x HEAD                    => ALLOW
AGENTS_OFF: git bundle create /tmp/b.bundle main       => ALLOW   ← запись файла
AGENTS_OFF: git replace HEAD HEAD~1                     => ALLOW
контроль (перечисленные глаголы — ловятся):
AGENTS_OFF: git commit -m wip                           => DENY
AGENTS_OFF: git push origin main                        => DENY
AGENTS_OFF: git worktree add /tmp/w feature/x           => DENY
```
И то же в обычном режиме, вне стопа — `git subtree push` обходит правило PUSH целиком:
```
git subtree push --prefix=dist origin main (рабочий репо) => ALLOW   ← доставка в main
контроль git push origin main                             => DENY
контроль git send-pack origin main                        => DENY
```
`git subtree` на ЭТОЙ машине не установлен (Apple Git 2.50.1, `git subtree --help` → нет), поэтому
именно subtree-пуш здесь пока теоретичен — но subtree это штатный опциональный компонент git
(homebrew, большинство Linux), а `git config`/`notes`/`replace`/`bundle` — встроенные и есть везде;
их обход стопа воспроизводится на этой же машине.

**ПОСЛЕДСТВИЕ.** Инвариант самого хука («ЛЮБАЯ запись запрещена… мутирующий git») ложен: под
нажатой кнопкой полного стопа проходят мутации git. Худшее — `git config core.hooksPath …` или
`git config alias.x '!команда'` под стопом задаёт исполнение произвольного кода при следующей
git-операции; `git subtree push origin main` (где subtree установлен) доставляет в main мимо обеих
кнопок и мимо правила PUSH. Ни один из этих путей не залочен и allow-листом (`git config --get*`
разрешён, но не `git config <set>`; `git subtree*` не разрешён вовсе → решает недетерминированный
классификатор, а структурный бэкстоп открыт).

**ЧТО ЧИНИТЬ.** Перечень глаголов после `git` обречён отставать так же, как перечень имён MCP до
круга 6. Под `AGENTS_OFF` надёжнее инвертировать: разрешать только ЧИТАЮЩИЕ git-подкоманды
(`SSH_RO_SUB["git"]` уже перечисляет их — `status|log|diff|show|rev-parse|…`), всё остальное
(включая `git <группа> <глагол>`) — DENY (fail-closed). Для правила PUSH — либо добавить `subtree`
в разбор (`git subtree push` = пуш), либо, симметрично, распознавать `push`/`send-pack` не только
сразу после флагов, но и после известной группы. Плюс юнит доктора: перебор
`git subtree push`/`git config <set>` под стопом обязан дать DENY.

## 2. `waiting-queue.sh`: тильда-фенс `~~~` не считается код-блоком, а CRLF-источник оставляет `\r` внутри строки очереди

**КЛАСС:** незакрытая щель разбора, который чинил круг 6 (маркер в код-блоке / пустой маркер).
Backtick-фенсы, пустой маркер, отступ и EOF-без-перевода отработали верно; две формы из того же
класса остались.

**ЧТО.** Отслеживание фенсов (`waiting-queue.sh:97`) переключает состояние только на строке,
начинающейся с ```` ``` ````. Markdown допускает и тильда-фенс `~~~` — он не переключает состояние,
и маркер `@ЖДЁТ:` внутри `~~~`-блока попадает в очередь как настоящая развилка. Отдельно: разбор
строки `ln="${raw%%:*}"; text="${raw#*:}"` (`:96`) не снимает `\r`, поэтому у CRLF-файла возврат
каретки уезжает в середину печатаемой строки очереди.

**ВОСПРОИЗВЕДЕНИЕ** (песочная доска):
```
nested.md: @ЖДЁТ внутри ~~~ … ~~~   → «- внутри тильда-фенса · `nested.md:3`»   ← пример как развилка
crlf.md (CRLF): «- развилка в CRLF файле · `[[c]]`\r · `crlf.md:2`»             ← \r в середине строки
контроль: маркер в ```-блоке, пустой маркер, отступ — В ОЧЕРЕДЬ НЕ ПОПАЛИ ✓
```
`od -c` подтвердил `] ] \r · ` внутри строки crlf.

**ПОСЛЕДСТВИЕ.** Пример `@ЖДЁТ:` из документации, оформленный тильда-фенсом, засоряет очередь
Президента (та же болезнь, ради ухода от которой перешли на структурный маркер). CRLF-строка в
терминале визуально портится: каретка перескакивает на начало и хвост затирает начало строки.
Обе — низкой частоты (на доске почти всегда backtick и LF), но воспроизводимы.

**ЧТО ЧИНИТЬ.** Переключать `in_code` и на строке, начинающейся с `~~~` (не только ```` ``` ````);
снять `\r` при разборе строки (`text="${text%$'\r'}"` или прогон входа через `tr -d '\r'`). Заодно
у табличной развилки в короткий текст утекает хвостовой ` |` ячейки — косметика, чинится тем же
проходом.

## 3. `session-end.sh`: авто-коммит памяти в detached HEAD уходит в «висячий» коммит — страховка молча не срабатывает

**КЛАСС:** страховка, которая в одном состоянии репозитория тихо не выполняет свою работу.

**ЧТО.** Авто-коммит (`session-end.sh:101-105`) делает `git add -A` + `git commit` без проверки, что
HEAD указывает на ветку. В detached HEAD коммит создаётся поверх отделённой головы, то есть не
принадлежит ни одной ветке; следующий `checkout` делает его недостижимым, и он уходит под gc. Весь
вывод глушится `2>/dev/null`, поэтому наружу ничего не сообщается.

**ВОСПРОИЗВЕДЕНИЕ** (песочный vault, `git checkout --detach`, несохранённое изменение, запуск
`session-end.sh` с `STACK_VAULT`/`AGENT_VAULT` на песочные каталоги):
```
detached-vault: log → «авто-коммит памяти…» поверх detached; symbolic-ref HEAD → (HEAD отделён)
empty-vault (без единого коммита): первый коммит создан корректно ✓
```
Коммит есть, но он вне ветки: при следующем переключении памяти он потерян.

**ПОСЛЕДСТВИЕ.** В detached HEAD «durable-координация», ради которой авто-коммит и заведён (память
не пролежала неделю без коммита), не выполняется: коммит формально сделан, фактически потеряется, и
ни строки предупреждения. Вероятность низкая (vault редко бывает в detached HEAD — например, если
руками сделали `checkout <sha>` и не вернулись), но именно в этом состоянии страховка нужнее всего.

**ЧТО ЧИНИТЬ.** Перед авто-коммитом проверять `git -C "$v" symbolic-ref -q HEAD` — при detached
HEAD пропустить коммит и оставить след (в stderr доктора или varn'ом «vault в detached HEAD, память
не закоммичена»), чтобы состояние было видно, а не проглочено.

## Гипотезы (без полного воспроизведения)

- **MCP: read-first перевес открывает гипотетический write-инструмент с читающим первым словом.**
  `MCP_READ_FIRST` (`guard.sh:233-235`) перевешивает `MCP_WRITE_NAME` — и это верно для
  `get_created_pages`/`list_deployments`. Но если сервер назовёт ПИШУЩИЙ инструмент читающим первым
  словом, он пройдёт полный стоп: проверил перебором — `resolve_issue`, `resolve_ticket`,
  `check_out_branch`, `status_transition_issue`, `view_delete`, `history_rewrite` под `AGENTS_OFF`
  → ALLOW (в трекерах «resolve/transition issue» — это запись-переход). В ЖИВОМ ростере такого
  инструмента нет (taiga/wiki/basic-memory/serena — все чтения глагол- либо объект-первые и
  корректны, все контроли верны), поэтому гипотеза, а не находка. Закрывается тем же fail-closed под
  стопом, что предложен в находке 1 круга 6 (разрешать только чит-глагол, остальное DENY). Ложных
  ЗАПРЕТОВ перевес не даёт — он только разрешает.
- **`secret.sh`: при отсутствии файла реестра в stderr течёт «No such file or directory».**
  `get` несуществующего секрета при пустом реестре: `$(tr … < "$REGISTRY" 2>/dev/null)` — редирект
  открывает несуществующий файл раньше `tr`, и сообщение шелла уходит в НЕ подавленный stderr
  (`secret.sh:54`). Значение секрета при этом не печатается (проверено), инъекция имени отбита
  (`name_ok`), имя с пробелами отклонено — то есть это косметический шум на уже-ошибочном пути, а не
  утечка. Чинится `[ -f "$REGISTRY" ]` перед `tr`.

## Что проверил и нашёл исправным (туда не возвращаться)

- **Починка круга 6 №1 (guard, объект-первые имена MCP) держит.** Под песочным `AGENTS_OFF`:
  `iva-write__confluence_create_page`/`jira_create_issue`/`confluence_delete_page` → DENY;
  объект-первые ЧТЕНИЯ `confluence_get_page`/`confluence_search_pages` → ALLOW; глагол-первые
  контроли `create_page` → DENY, `get_page`/`list_issues`/`search_pages` → ALLOW. Обе стороны
  перевеса `MCP_READ_FIRST`/`MCP_WRITE_NAME` верны для живого ростера.
- **Починка круга 6 №2 (доктор, глубокая сверка хуков) держит полностью.** Живой прогон: `drift`
  пуст (ложных срабатываний от `__HOME__` нет). Синтетика на копии шаблона: ловит добавленное
  событие, изменённый `timeout`, изменённый `matcher`, расхождение `statusLine`, расхождение `env`,
  удалённый хук внутри события — каждое печатается. `model` из сверки исключён и не даёт дрейфа.
- **Починка круга 6 №3 (`pr-queue.sh`, почта по репозиторию) держит.** Запуск из `/tmp`, где
  глобальная почта (`…yandex.ru`) НЕ совпадает с автором ветки: ветка `feat/mine` всё равно ПОКАЗАНА,
  потому что почта прочитана из локального конфига самого репозитория (`local-dev@work.local`), и она
  совпала с автором. Раньше здесь очередь молча пустела.
- **Починка круга 6 №4 (`waiting-queue.sh`) держит в проверенной части.** Backtick-код-блок,
  пустой маркер `@ЖДЁТ:`, маркер с отступом (код), маркер в конце файла без перевода строки — все
  НЕ попали / попали корректно. Табличная развилка и настоящая развилка — на месте. (Тильда-фенс и
  CRLF — находка 2.)
- **Починка круга 6 №5 (`settings.example.json` синхронизирован) держит.** Шаблон — валидный JSON;
  ВСЕ команды хуков существуют (`session-start/end`, `post-/pre-compact`, `guard`, `stop-reminder`,
  `stop-nudge`, `permission-denied`, `worker-log`, `diff-shorten`, `pr-reminder`, `tool-failure-log`)
  и `statusline.sh` тоже; `__HOME__` разворачивается; живой `drift` пуст. `diff-shorten.sh` и
  `stop-nudge.sh` присутствуют в шаблоне.
- **Правило PUSH — новые формы (мой блок).** Проверены и корректны: `--repo=url` без ветки → DENY;
  URL вместо remote в main → DENY, в feat → ALLOW; `HEAD:refs/heads/main` и `HEAD:main` → DENY;
  несколько refspec (`feat main`, `feat:feat main:main`) → DENY на main; `git -c … push … main` →
  DENY; `cd <репо> && git push … main` из чужого cwd → DENY; `send-pack … main`/`… refs/heads/main`
  → DENY; `+refspec` → DENY; `--mirror` → DENY; `-o ci.skip … main` → DENY; `$BR` (рантайм-ветка) →
  DENY fail-closed; доставка feat-ветки → ALLOW. Единственная дыра PUSH — `git subtree push`
  (находка 1).
- **`secret.sh` — валидация и отсутствие утечки.** Имя с пробелами и имя с `$(…)` отклонены
  (`name_ok`); несуществующий секрет — значение не печатается; `env` без команды — usage, rc=1;
  `list` на пустом — корректно. (Мелочь про stderr — в гипотезах.)

## НЕ проверено (в следующий круг)

- **`session-end.sh` при активном ребейзе/незакрытом merge-конфликте и на огромном числе файлов** —
  проверены только detached HEAD и пустой репозиторий. Коммит поверх конфликта (маркеры в память)
  или во время `rebase` не воспроизводился.
- **`pre-compact.sh`/`post-compact.sh` — не дошли круги 2–7.**
- **`secret.sh set`/`rm` вживую и путь «нет утилиты `security`»** — только чтением кода (на macOS
  `security` присутствует, ветку отсутствия не воспроизвести без подмены PATH).
- **`git subtree push` на машине, где subtree установлен** — здесь subtree отсутствует, обход PUSH
  подтверждён только разбором гейта, не живым пушем.
- **Опрос удалённых серверов `tools/list`'ом вживую** — сеть под классификатором; классы имён
  закрыты перебором известных, полный перечень с сервера не снят.
- **SSH-классификатор `guard.sh` построчно** — по-прежнему по зелёным тестам доктора.
- **Поведение на чистой машине** (нет node/python-yaml) — только чтением.
