# Аудит стека круг 6 — находки ревизора-ломателя 2026-08-09

Только чтение, кроме этого файла; все пробы — в песочнице скратчпада (подменённый `HOME`,
одноразовые vault и репозитории, песочная кнопка `AGENTS_OFF`; живые кнопки, реестр и память
не тронуты — головы `stack-vault` и `tacticum-vault` до и после совпадают). Области круга: шесть
починок круга 5 · `pr-queue.sh` целиком · `waiting-queue.sh` целиком · паритет
`settings.example.json` против живого · списки инструментов удалённых MCP через гейт под стопом.

**Пустого круга снова не вышло — пять доказанных находок, по убыванию последствия.** Все шесть
починок круга 5 держат (перепроверены — см. «нашёл исправным»). Главный итог круга — то, чего пять
предыдущих кругов не увидели: **под полным стопом `AGENTS_OFF` проходит ВЕСЬ пишущий сервер
`iva-write`** (Confluence/Jira), потому что его инструменты названы объект-первыми

## 1. Под полным стопом `AGENTS_OFF` проходит ВЕСЬ пишущий сервер `iva-write` — имена объект-первые (`confluence_create_page`), а гейт ищет глагол только в начале имени

**КЛАСС:** дыра гейта, худшее направление (запись мимо аварийного стопа) + это не один инструмент,
а целый живой write-сервер. Тот же класс, что `canvas`/`activate_project` (круги 4–5), но масштаб
иной.

**ЧТО.** Под `AGENTS_OFF` инструменты MCP, которых нет в явном списке `MCP_WRITE`, классифицирует
`MCP_WRITE_NAME` (`guard.sh:216-219`) — регулярка с якорем `^`: глагол должен стоять ПЕРВЫМ словом
листа имени. `taiga`/`wiki-mcp` называют инструменты глагол-первыми (`create_issue`, `update_page`,
`delete_page`) — ловятся. А `iva-write` (Atlassian MCP, живой, local-скоуп `~/tacticum`, в докторе
`✔ iva-write ... токен 43`) называет их ОБЪЕКТ-первыми: `confluence_create_page`,
`confluence_update_page`, `confluence_delete_page`, `jira_create_issue`, `jira_update_issue`. Глагол
в середине — якорь `^` не срабатывает, инструмент проходит как чтение.

**ВОСПРОИЗВЕДЕНИЕ** (песочный `HOME` с `AGENTS_OFF`, `AGENT_ROLE=lead`, перебор через `guard.sh`):
```
mcp__iva-write__confluence_create_page => ALLOW   ← запись в Confluence под полным стопом
mcp__iva-write__jira_create_issue      => ALLOW
mcp__iva-write__confluence_delete_page => ALLOW
контроль (то же имя, глагол первым — как у taiga):
mcp__iva-write__create_page  => deny
mcp__iva-write__delete_page  => deny
mcp__iva-write__update_issue => deny
```
Гейт под стопом РАЗБИРАЕТ этот сервер (быстрый путь `guard.sh:57-58` при активном `AGENTS_OFF`
пропускает через python ВСЁ) — то есть отказ должен был бы сработать, но не срабатывает.
Для сравнения весь `taiga`/`wiki-mcp` под тем же стопом: запись (`create_issue`, `update_page`,
`delete_page`, `add_comment`, `link/unlink_user_story_to_epic`) — DENY, чтение — ALLOW.

**ПОСЛЕДСТВИЕ.** Инвариант «при `AGENTS_OFF` не меняется ничего» ложен на целом сервере, причём
пишущем во ВНЕШНИЕ системы (Confluence, Jira). Аварийный стоп, нажатый в `~/tacticum`, не держит
самый релевантный там write-инструмент. Тот же дефект у `tacticum-mcp` (`kb_update_artefact`,
`submit_feedback`, `provision_installation` — глагол не первый или не из списка), но он сейчас
не одобрен и 401, поэтому не грузится; `iva-write` — грузится.

**ЧТО ЧИНИТЬ.** Якорь `^` в `MCP_WRITE_NAME` предполагает глагол-первое имя — это допущение неверно
для объект-первых серверов. Искать глагол как отдельное СЛОВО в любом месте листа:
`(?:^|_)(create|new|add|…|submit|provision|…)(?:_|$)` (и дополнить список глаголами `submit`,
`provision`, `finalize`, `initiate`). Но перечень глаголов обречён отставать так же, как перечень
имён; надёжнее — под `AGENTS_OFF` инвертировать логику для НЕизвестных серверов: разрешать только
инструменты с чит-глаголом в имени (`get/list/read/search/find/view/…`), всё остальное — DENY
(fail-closed, как уже сделано для `ssh-manager`). Плюс юнит доктора: перебор имён `iva-write`
под стопом обязан дать DENY на `confluence_create_page`.

## 2. Доктор рапортует «шаблон settings.example.json совпадает с живым» — а он НЕ совпадает прямо сейчас: `diff-shorten.sh` и `stop-nudge.sh` есть в живом и отсутствуют в шаблоне

**КЛАСС:** зелёная проверка, которая не может провалиться на том, ради чего написана — сверка
сравнивает только ИМЕНА событий и права, но не сами определения хуков. Актив, а не гипотеза:
расхождение существует на сегодняшнем конфиге.

**ЧТО.** Сверка (`stack-doctor.sh:557-565`) считает расхождением: разные верхние ключи
(`set(a)^set(b)`), разные ИМЕНА событий hooks (`set(a.hooks)^set(b.hooks)`), разные множества
правил `allow/deny/ask`. Поддерево внутри события, `statusLine`, `env` — НЕ сравниваются. Пока имена
событий совпадают, любое различие хуков ВНУТРИ события проходит молча.

**ВОСПРОИЗВЕДЕНИЕ** (нормализация — точная копия функции доктора, `norm` c заменой `$HOME`):
```
верхние ключи — совпадают; имена событий hooks — совпадают  →  доктор: «совпадает» (зелёно)
глубокое сравнение того, что проверка НЕ смотрит:
  PostToolUse: в live есть [Edit|Write|MultiEdit|NotebookEdit] hooks/diff-shorten.sh — в шаблоне НЕТ
  Stop:        в live есть []                                   hooks/stop-nudge.sh   — в шаблоне НЕТ
```
Синтетическая проба подтвердила и остальные слепые зоны: подменил у live лишний хук под
`PreToolUse`, другой `timeout` у guard, другую команду `statusLine`, другое значение `env.FOO` —
функция доктора вернула `DRIFT=[]` (пусто). Живой доктор сейчас печатает
`ok шаблон settings.example.json совпадает с живым конфигом`.

**ПОСЛЕДСТВИЕ.** Ровно то, против чего проверка писалась (её коммент: «на новой машине часть
механизмов просто не поднимется»): развернув стек из `settings.example.json`, новая машина молча
не получит `diff-shorten.sh` (сокращение диффов) и `stop-nudge.sh` (подталкивание застрявшей роли).
Зелёная строка уверяет, что перенос воспроизведёт рабочий конфиг, — а он не воспроизведёт.

**ЧТО ЧИНИТЬ.** Сравнивать поддеревья целиком, а не множества ключей: `norm(a.hooks)==b.hooks`,
`a.statusLine==b.statusLine`, `a.env==b.env`; при неравенстве печатать, какое событие/ключ
разошлись. Отдельно — синхронизировать шаблон с живым (добавить `diff-shorten.sh`, `stop-nudge.sh`),
но это правка в стек, то есть не мне: передать в контур стека.

## 3. `pr-queue.sh` фильтрует «свои ветки» по почте из git config ТЕКУЩЕГО каталога, а не каждого репозитория — при несовпадении личности очередь молча пустеет

**КЛАСС:** молчаливо-пустая очередь — ровно тот исход, который сам скрипт объявил худшим («пустой
фильтр лучше молчаливо пустой очереди»). Сейчас латентно: глобальная почта случайно совпадает с
авторами веток.

**ЧТО.** `ME` читается ОДИН раз (`pr-queue.sh:40`): `git config --get user.email` — без `-C`, то
есть из cwd скрипта. Дальше этой одной личностью фильтруются ветки во ВСЕХ сканируемых репозиториях
(`:68`). Но `git config user.email` разрешается по каталогу: из репозитория с локальным
`user.email` вернётся он, из не-репозитория — глобальный. Хук зовётся из `session-start.sh` с тем
cwd, в котором открыли сессию.

**ВОСПРОИЗВЕДЕНИЕ** (песочный репозиторий: ветка `feat/cyr-ветка` доставлена на `origin`, не влита,
автор `yenvaesh@onet.pl`; главная ушла вперёд — `отстал 2`):
```
A) cwd = сам репо (локальный user.email=yenvaesh)      → ветка ВИДНА:
     !  дн  отстал  репозиторий   ветка
        0      2    repoA         feat/cyr-ветка
B) cwd = /tmp (git отдаёт ГЛОБАЛЬНУЮ почту yandex.ru)  → та же ветка ИСЧЕЗАЕТ:
     очередь мержа: пусто — недоставленных веток нет
```
Механизм: из `/tmp` `git config --get user.email` = `aleksandr-shulga-0507@yandex.ru`, у ветки
автор другой → отфильтрована → «пусто». Сейчас на живых репозиториях не бьёт: `~/tacticum/helm`
локального `user.email` не имеет, глобальный совпадает с авторами веток (`git -C helm` → yandex.ru,
105 веток того же автора). Но стоит любому рабочему репозиторию завести локальную рабочую почту
(обычная практика) или сессии стартовать из репо с иной личностью — очередь молча опустеет.

**ПОСЛЕДСТВИЕ.** Баннер старта покажет пусто при реально висящих ветках — вернётся трение №1
(ветка протухает, никто не отвечает за свежесть), против которого весь скрипт и заведён, и
вернётся незаметно.

**ЧТО ЧИНИТЬ.** Читать почту ПО КАЖДОМУ репозиторию внутри `scan_repo`:
`me="$(git -C "$repo" config --get user.email)"` и сравнивать с `author` этого же репо. Так каждый
репозиторий знает, кто в нём коммитит; одна личность из cwd — неверная модель.

## 4. `waiting-queue.sh`: маркер `@ЖДЁТ:` внутри код-блока считается настоящей развилкой — пример из инструкции попадает в очередь Президента

**КЛАСС:** предмет спутан с упоминанием предмета — тот самый класс, ради ухода от которого скрипт
перешёл на структурный маркер (его коммент, `:60-62`). Прямой ответ на вопрос постановки «должен ли
маркер в код-блоке считаться?»: сейчас считается, а не должен.

**ЧТО.** Очередь собирается `grep -nF "$MARK"` (`:93`) по всему тексту файла — фенсы ```` ``` ````
не учитываются. Любой файл доски, где маркер ПОКАЗАН (карточка-шаблон, инструкция, отчёт круга,
цитирующий `@ЖДЁТ:`), отдаёт свой пример в очередь. Свой выходной файл скрипт исключает по basename
(`:83`) — и сам пишет в него пример маркера в код-блоке (`:115`), — но только его; чужие файлы
с примером не исключены.

**ВОСПРОИЗВЕДЕНИЕ** (песочная доска: `howto.md` с примером `@ЖДЁТ:` внутри ```` ``` ````,
`lead-real.md` с настоящей развилкой):
```
## Ждёт решения — 3
- настоящая развилка — мержить ли ветку feat/x до релиза · [[card-x]] · `lead-real.md:7`
- это ПРИМЕР из инструкции, решать тут нечего · [[какая-то-карточка]] · `howto.md:10`   ← из код-блока
- @ЖДЁТ · `lead-real.md:9`                                                              ← находка 5
```

**ПОСЛЕДСТВИЕ.** В очередь, которую Президент читает как список открытых развилок, попадают
примеры из документации. «Треть строк — мусор, читают один раз» — точная формулировка болезни из
шапки самого скрипта.

**ЧТО ЧИНИТЬ.** При проходе по файлу отслеживать состояние «внутри ```` ``` ````-блока» (считать
фенсы) и пропускать строки внутри него; заодно — строки, начинающиеся с 4+ пробелов (indented
code). Маркер живёт в прозе карточки, не в примере.

## 5. `waiting-queue.sh`: пустой маркер `@ЖДЁТ:` даёт мусорную строку `@ЖДЁТ` в очереди — `IFS=:` съедает завершающее двоеточие маркера, и проверка на пустоту не срабатывает

**КЛАСС:** проверка на пустой пункт (`[ -z "$short" ]`, `:90`) обходится из-за хрупкого парсинга
вывода `grep -n`.

**ЧТО.** Строки `grep -n` разбираются `while IFS=: read -r ln text` (`:87`). Маркер САМ кончается
двоеточием (`@ЖДЁТ:`). Для пустого маркера `grep` даёт `9:@ЖДЁТ:` — в полном контексте скрипта
`read` с `IFS=:` отбрасывает завершающее двоеточие, и `text` становится `@ЖДЁТ` (без двоеточия).
Тогда `sed "s/.*@ЖДЁТ:[[:space:]]*//"` не находит якоря `@ЖДЁТ:` (двоеточия в тексте уже нет),
подстановки нет, `short` остаётся `@ЖДЁТ` — непусто, строка печатается.

**ВОСПРОИЗВЕДЕНИЕ** (трейс живого хука и дословно извлечённый блок `:81-105` дают одно и то же):
```
ln=9  text=<@ЖДЁТ>  short=<@ЖДЁТ>   → EMIT «- @ЖДЁТ · lead-real.md:9»
```
Проба фикса (сплит по ПЕРВОМУ двоеточию вместо `IFS=:`):
```
ln="${line%%:*}"; text="${line#*:}"   →  text=<@ЖДЁТ:>  short=<>  → ПРОПУЩЕН (пусто)  ✓
```

**ПОСЛЕДСТВИЕ.** Лид, поставивший маркер и ещё не дописавший фразу (заготовка, опечатка, шаблон),
получает в очереди Президента бессмысленную строку `@ЖДЁТ`. Мелко, но это ровно «мусор в очереди»,
против которого выбран структурный маркер.

**ЧТО ЧИНИТЬ.** Не разбирать вывод `grep -n` через `IFS=:` (в тексте есть двоеточия, и маркер ими
кончается): сплит по первому двоеточию параметрическим расширением — `ln="${line%%:*}";
text="${line#*:}"`. Тогда завершающее двоеточие маркера сохраняется, `sed` срабатывает, пустой
маркер отсеивается. Проверено — фикс убирает строку `@ЖДЁТ`, настоящие пункты не трогает.

## Гипотезы (без полного воспроизведения)

- **Title-case в сверке редакций доктора.** `stack-doctor.sh:952` ловит `вернул`/`ВЕРНУЛ`, но не
  `Вернуло` (первая заглавная, остальные строчные). В живых текстах слово стоит после даты в
  середине предложения (строчное) либо целиком заглавным для акцента — Title-case не встречался,
  поэтому гипотеза, а не находка. Закрыть формой `[Вв]ернул|ВЕРНУЛ` за один символ.
- **`tacticum-mcp` — тот же класс дыры, что находка 1** (`kb_update_artefact`, `submit_feedback`,
  `provision_installation`, `kb_finalize_upload` проходят под стопом), но сервер не одобрен и 401 —
  Claude Code его не грузит, поэтому пока не пожар. Починка находки 1 закроет и его.
- **`waiting-queue.sh`: троттлинг 30 мин привязан к mtime выходного файла** — если правка доски
  случилась внутри окна, очередь на старте будет устаревшей до получаса. Осознанный компромисс
  (в шапке), не дефект; упоминаю, чтобы не переоткрывали.
