# Границы прав роли стек — полные права на стек, полный запрет на серверы и Тактикум

**Решение Президента, 2026-08-09.** Права роли `stack` расширяются до полных внутри стека и
сужаются до нуля снаружи. Ключевая мысль, которую он проговорил отдельно: **у каждой роли свои
настройки**, и границы роли `stack` не переносятся на рабочие роли.

## Границы

**Граница проходит по «локально / наружу», а не по каталогам.** Это уточнение самого Президента,
после того как я прочитал его первую формулировку наоборот: *«главное ты работаешь локально, то есть
ты на моей машине работаешь и на четырёх личных удалённых репозиториях в GitHub»*.

| Зона | Роль `stack` | Рабочие роли (director/lead/воркеры) |
|---|---|---|
| Вся машина локально: `~/.claude`, `~/claude-stack`, `~/stack-vault`, **`~/tacticum*` тоже** | **полные права, запретов нет** — включая файлы, бывшие неприкосновенными | без изменений |
| 4 личных репозитория на GitHub (`claude-stack`, `claude-config`, `work-vault`, `stack-vault`) | **запретов нет**, пуш в любую ветку | без изменений |
| Серверы через `ssh-manager` | **полный запрет, включая чтение** | **без изменений** — читать свободно, менять по устному ОК ([[adr-server-read-free-write-by-ok]]) |
| Удалённые репозитории заказчика (GitLab/GitHub Тактикума) | **наружу ничего** — ни пуша, ни мержа | без изменений: feature-ветку пушит, `main` никогда |

Проще всего запомнить так: **локально можно всё; наружу — только четыре личных репозитория; на
серверы — нельзя вовсе.** Локальные правки в рабочих каталогах (например `~/tacticum/.mcp.json`)
ролью `stack` разрешены — именно так 09.08 чинились токены MCP.

## Почему ssh роли стека не нужен — проверено, а не предположено

За всю историю работы над стеком сервер не понадобился ни разу. Даже проверка ssh-гейта делается без
сети: разбор команд гоняется пробами на классификаторе (`probe-ssh-direct-krug10-2026-08-06.py`,
46/46, ноль подключений). Президент предложил выдать `docker logs`, если он нужен для правок стека —
ответ «не нужен, и не выдавай про запас».

## Механика, а не текст

Границы держит `guard.sh`, который читает `AGENT_ROLE` (роль задаётся в `roles.zsh` при старте окна).
Значит правило пишется по РОЛИ СЕССИИ, а не по тому, кто спавнил: **воркер под рабочей ролью — ssh
есть, воркер под `stack` — нет**. Иначе правило либо отберёт ssh у рабочих воркеров, либо не отберёт
у моих. Это прямое требование Президента: *«нужно прописать настройки под воркеров на ролях»*.

**Расширение прав — это удаление проверок, и проверять его надо прогоном, а не чтением кода.**
Установлено 09.08 пробой: правку собственных разрешений в `settings.json` блокирует **классификатор
харнесса**, а не `guard.sh` — то есть часть границ живёт вне моего гейта, и снять их может только
рука Президента. Это и есть класс, ради которого существует `~/claude-stack/pending-apply/`.

## Что отменяет

Ослабляет для роли `stack`: правила CONFIG и SENTINEL (запрет записи в периметр через Bash), статус
неприкосновенных файлов (`CLAUDE.md`, `memory-protocol.md`, `agent-company.md`), апрув на мерж в
`main` личных репозиториев. Не отменяет ничего для рабочих ролей.
